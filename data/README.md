# data/

Build-specific game data, generated offline and committed, so the companion pays no lookup cost at play time.

## items_<build>.json: weapon and armour catalog

- **Design:** `docs/design/robustness-and-item-catalog.md`, section 2.
- **Generated by:** `tools/build_catalog.py`, which drives `mod/scripts/catalog.lua` on the live server through `debug_run`. Regenerate after every game patch:
  ```
  .venv\Scripts\python.exe -m tools.build_catalog                  # loaded items + registry + LoadAsset batches
  .venv\Scripts\python.exe -m tools.build_catalog --no-load        # loaded items only
  .venv\Scripts\python.exe -m tools.build_catalog --no-load --notifies   # + swing timing (what produced the 26161880 file)
  .venv\Scripts\python.exe -m tools.build_catalog --merge-only logs\catalog\<build>_<ts>   # re-normalise, no server
  ```
- **Raw output:** the mod writes its raw per-call files (`dw_catalog_raw/1`) to `logs/catalog/<build>_<ts>/`, which is gitignored. Only the normalised file lives here.
- **Source:**
  - Loaded items: `FindAllOf` on each concrete data class.
  - Unloaded items: `IAssetRegistry::GetAssetsByClass`, then UE4SS `LoadAsset`.
  - Field names: the build's reflection dump (`Dominion.hpp`: `UItemData`, `UEquipmentData`, `UHeldEquipmentData`, `UWearableEquipmentData`, `UPlayerAction`, `UPlayerMeleeAttackAction`, `UPlayerAttackData`, `UPlayerRangedAttackCollection`).

### Top level (`schema: "dw_items/1"`)

| Key | Meaning |
|---|---|
| `build` | Game/server build ID (e.g. `26161880`). The catalog is only valid for this build. |
| `generated_at` | UTC timestamp. |
| `source` | `raw_files`, `registry_count` (held/wearable assets the registry knows), `described_count`, `missing_from_catalog` (registry paths never described, e.g. load failures or a run stopped early), `errors` (the first 200 raw errors). |
| `items` | Map of item id → item (below). The id is the asset name (`ITEM_Sword_Mithril`); on a name clash, `<name>@<mount root>`. |
| `attack_sets` | Map of action class path → attack set (below), for every action any item references. |
| `attacks` | Map of attack-data class path (`BP_Player_<Cat>_AttackN_C`) → per-swing data read from the class default object: `damage` (`DamageAmount`), `damage_class(_name)` (`EDamageClass`), `stamina_cost`, `special_charge_cost`, `force`, `uses_weapon`, `single_target`, `damage_shapes` (count of `TimedDamageShapes`), `max_move_speed`, `next` (`NextAttackClass`), `next_no_perk` (`NextAttackClassNoRequiredPerk`, the short-combo end), `required_perk_for_next`, and with `--montage`/`--notifies` a `timing` object from the attack's montage (`RootMotionAttackData.Montage`, else `InPlaceAttackData.Montage`): `montage`, `length` and `rate` (`SequenceLength`, `RateScale`), `input_window` [start, end] (`AnimNotifyState_AttackInputWindow_C`, the combo input window), `damage_points` (`AnimNotify_AttackDamagePoint_C`), `reset_chain` (`AnimNotify_AttackResetChain_C`) and `allow_move` (`AnimNotify_AllowMovementInput_C`), all in seconds from the swing start. |
| `ranged_collections` | Map of `UPlayerRangedAttackCollection` class path → `quick_attack`, `full_attack` (attack paths), `trick_shot_damage_multiplier`, `max_charge_up`, `allow_move_quick`. |
| `category_action_fallback` | Static category → primary-action table (from the object dump), used only when an item's own `PrimaryActionClass` could not be read. |

### Item: common fields

| Field | Source / meaning |
|---|---|
| `id`, `path` | Asset name and full object path (`/Root/.../ITEM_X.ITEM_X`), the path to `StaticFindObject` or `LoadAsset`. |
| `name`, `flavour` | `UItemData.Name` and `FlavourText` (FText → string). |
| `kind` | `held` (`UHeldEquipmentData` and subclasses) or `wearable` (`UWearableEquipmentData` and subclasses). |
| `class` | Concrete data class, e.g. `HeldEquipmentData`, `ShieldData`, `FishingRodHeldEquipmentData`, `JewelleryData`. |
| `category` | Lower-case category from the asset folder (`.../Equipment/Held/<Folder>/`, or `.../Equipment/<Slot>/` for armour) or from the subclass. Examples: `sword`, `mace`, `greatsword`, `greataxe`, `hammer`, `dagger`, `scimitar`, `bow`, `crossbow`, `staff`, `wand`, `axe` (the Hatchet folder), `pickaxe`, `torch`, `shield`, `fishing_rod`, `spade`, `seed`, `club`, `test` (status-effect test items: ignore), and `head`/`body`/`legs`/`cape`/... for armour. |
| `category_tag`, `filter_tags`, `granted_tags` | Gameplay tags: `UItemData.Category`, `ItemFilterTags`, `UEquipmentData.GrantedTags`. |
| `slot` | Normalised `UEquipmentData.Slot` (`ELoadoutSlotStrategy`): `head`, `body`, `legs`, `cape`, `trinket`, `necklace`, `hand_any`, `right_hand`, `left_hand`, `two_handed`, `ammo`, ... `slot_strategy` keeps the raw enum name. |
| `hand_preference` | `UEquipmentData.HandPreference` (`right`/`left`). |
| `tier`, `power_level`, `is_weapon`, `weight`, `durability`, `max_stack` | `UEquipmentData.Tier`, `UItemData.PowerLevel`, `bIsAWeapon`, `Weight`, `BaseDurability`, `MaxStackSize`. |
| `custom_stats` | `UItemData.CustomStatDetails` (`[{name, value}]`, display strings). |
| `requirements` | `perk_required`, `recipe_required`, `entitlement_required` (object paths) when set. |
| `role` | `weapon`, `tool`, `shield`, `armour` or `other`. Derived from `is_weapon` and the category. |
| `source` | How the mod reached it: `loaded` (already in memory), `found`, or `loaded_now` (`LoadAsset` during the build). |

### Item: held only

| Field | Source / meaning |
|---|---|
| `held_actor_class` | `UHeldEquipmentData.HeldEquipmentActorClass` (soft class) as a class path, the class to `SpawnActor` (DISCOVERIES "Route 1: puppet dressed and armed"). `held_actor_class_inferred: true` means the mod returned only a package path and `.<Name>_C` was appended by convention. |
| `hand`, `socket` | Hand to equip in, and the mesh socket: `prop_r` (verified for the puppet) or `prop_l` (by convention, not yet verified). |
| `range_type` | `melee`, `ranged`, `magic` or `none`. From the primary action's class (`UPlayerMelee/Ranged/MagicAttackAction`), `RangedAttackCollection`, `MagicAttackCollection`, `AmmoType`, and the category. |
| `attacks` | Map of `primary`, `secondary`, `special`, `primary_sprint`, `primary_visceral`, `primary_jump` → attack set, from `UHeldEquipmentData.<X>ActionClass`. |
| `attack_source` | `item` (read from the item), `category_learned` (the majority action of other items in the same category), `category_table` (`category_action_fallback`), or absent. |
| `stats` | `damage_multiplier`, `additional_damage_multiplier`, `blocking_damage_negation`, `additional_blocking_damage_negation`, `stamina_cost_multiplier`, `crit_chance_increase`, `reload_duration`, `requires_reload`. |
| `damage_types` | `UHeldEquipmentData.DamageTypes` tags. |
| `ammo`, `required_ammo_tag`, `projectile_class` | `AmmoType` (`EHeldEquipmentAmmoType` name), `RequiredAmmoCategory`, `ProjectileClass`. |
| `pose` | `AnimationPoseType` (`Unarmed`/`Default`/`Ranged`). |
| `power_level_row` | `BaseHeldEquipmentPowerLevelRowHandle` (`{table, row}`); the actual base damage numbers live in that data table. |
| `ranged` | `{collection, quick_attack, full_attack}` for bows and crossbows. |
| `magic_collection` | `UPlayerMagicAttackCollection` class path for staves and wands. Its spell map is not read. |

**Attack set:**
- `action`: the `UPlayerAction` class, e.g. `PA_Attack_Sword_C`. Its CDO is the `Data` of `FPlayerActionInstance`.
- `kind`: `melee`, `ranged`, `magic`, `aim`, `block`, `harvest`, `evade` or `drop`.
- `name`: `ActionName`.
- `chain`: the attack-data classes in combo order, following `NextAttackClass`, starting with `AttackData`. `chain[0]` is the class to pass to `BP_PerformAttack` (DISCOVERIES, "Combat (E3)").
- `short_chain`: the chain without the `PerkV2_Attack_MeleeExtendCombo` perk (follows `next_no_perk` where set), when it differs from `chain`.
- `combo_ends`: short-combo finishers.
- `damage`: `DamageAmount` per step.
- `damage_class`.

### Item: wearable only

| Field | Source / meaning |
|---|---|
| `stats.armor_weight` | `ArmorWeight` (`None`/`Light`/`Medium`/`Heavy`). |
| `stats.warmth` | `WarmthMagnitude` (`EGameplayEffectMagnitude` name). |
| `data_row` | `WearableEquipmentDataTableRowHandle` (`{table, row}`): armour values live in that data table. |
| `male_mesh`, `female_mesh` | `UWearableEquipmentMeshData` object paths. |

Equip a wearable on the puppet by writing `PlayerEquipmentComponent.Current<Slot>Wearable` with the data object. This works for `head`, `body`, `legs` and `cape` (DISCOVERIES).

## ../mod/body/attack_data.lua: the combo table the mod loads

Generated from this catalog by `.venv\Scripts\python.exe -m tools.gen_attack_data` (newest `items_*.json`), so the mod never parses this JSON at runtime. It keeps only melee weapons (not `test` items): `items[<data path>] = {id, category, primary, special}`, `sets[<action class>] = {name, cdo, steps, short}` with per-step `next_ms` (end of the input window, at least the last damage point + 0.2 s), `reset_ms` (chain reset), `damage`, `special_cost`, and `categories[<category>]` = that category's usual primary set. Used by `mod/body/combat.lua`. Regenerate together with the catalog.

### Caveats

- Values come from class default objects and data assets, not from runtime-modified instances. Damage scaling by power level and data tables is not resolved.
- `category` comes from folder names. Check it when a new DLC root appears; a root is the first path segment, such as `/DowdunReach`, `/UmbralSands` or `/ScornedWilderness`.

## recipes_<build>.json: recipes, crafting/processing stations, unlocks

- **Design:** `docs/design/robustness-and-item-catalog.md` sections 18–19 (strict emulation); research section 5 of `docs/research/2026-10-25-scalable-agent-frameworks.md`.
- **Generated by:** `tools/build_recipes.py`, which drives the read-only `mod/scripts/recipe_dump.lua` on the live server through `debug_run`, one stage per call (recipes, stations, tables, player, items) with a ping and a crash-dump count after each. It also writes `mod/body/recipe_data.lua` (below). Regenerate after every game patch:
  ```
  .venv\Scripts\python.exe -m tools.build_recipes                               # live, all stages
  .venv\Scripts\python.exe -m tools.build_recipes --merge-only logs\recipes\<build>_<ts> --wiki-check
  ```
- **Raw output:** `logs/recipes/<build>_<ts>/NN_<stage>.json` (`dw_recipes_raw/1`, gitignored). The wiki cross-check downloads the wiki's `recipe` Bucket table once into `logs/recipes/wiki_recipe_bucket.json` and writes `logs/recipes/wiki_check_<build>.json` (the wiki is CC BY-NC-SA, so it stays out of git); only the summary counts land in this file.
- **Sources (Dominion.hpp, build 26161880):**
  - Recipes: `FindAllOf("RecipeData")` (1232 loaded at idle, incl. 7 `URuneRecipeData`): `ItemsConsumed`, `ItemsCreated`, `ExtraItemsCreated` + `ChanceToProduceExtraItems`, `AlternativeItemCreated` + `AlternativeItemChanceAttribute`, `FuelConsumedOverride`, `CraftTime`, `MaxCraftTime`, `CraftQuantityMultiplier`, `Min/MaxProcessingTime`, `SkillUsedToCraft`, `SkillXPAwardedOnCraft`, `VendorReputationRequirement`, `bIgnoreAutomaticUnlocks`.
  - Stations: the blueprint component templates `<BP>_C:CraftingStation_GEN_VARIABLE` / `:ProcessingStation_GEN_VARIABLE` (FindAllOf skips archetypes, so their paths come from the build's object dump) give the station class and its row handle; the rows come from `DT_CraftingStationsDataTable` (`FCraftingStationDataTableRow.LabeledRecipes`), `DT_ProcessingStationDataTable` (`FProcessingStationDataRow.Recipes`, `AcceptedFuels`, `ProcessingRate`, slots) and `DT_VendorDataTable`, read with the UE4SS `UDataTable:ForEachRow` Lua API. Live placed stations add `ValidRecipes` / `RecipesCache`.
  - Unlocks: every `DT_Progression_*` row (`FProgressionBundleRow`) with `UnlockedRecipes`, e.g. `ALL ITEMS[ Iron Ore ] AND ALL ACTORS[ BP_Station_Smelter_C ]`.
  - The connected player's `ProgressComponent.RecipesUnlocked` (the unlock mirror snapshot) and `InteractableDetector.InteractionRanges` (Short 250, Medium 350, Long 650, Fishing 1200 cm).

| Key | Meaning |
|---|---|
| `schema`, `build`, `generated_at` | `dw_recipes/1`, the build, UTC time. |
| `source` | `raw_files`, `counts` (recipes, stations, items, station components, tables, progression tables), `errors`. |
| `recipes` | Map recipe id (asset name; `<name>@<root>` on a clash) → `{id, path, class, inputs: [{item, path, count, name}], outputs: [...], stations: [station ids], station_kinds, craft_time, max_craft_time, craft_quantity_multiplier, processing_time: [min, max], extra?: {items, chance}, alternative?: {item, count, chance_attribute}, fuel_override?, tools: [], skill, xp, unlock: {bundles: [{table, row, query, manual, milestone}], ignore_automatic_unlocks}, vendor_reputation?, rune_type?, test?}`. `tools` is always empty: `URecipeData` has no "required but not consumed" field in this build. |
| `stations` | Map station TYPE id (the data-table row name; `@processing` on a name used by both tables) → `{id, kind: crafting\|processing, display_name, classes, class_names (the actor class words the census matches exactly), row, recipes, labels {menu label: [recipe ids]}, interaction {distance_name, range_cm, prompt}, accepted_fuels, processing_rate, max_resource_slots, max_fuel_slots, building (its BUILDPIECE), is_vendor, sources, live, test?}`. Rows with no loaded blueprint (e.g. Grill, Advanced Tannery) have no `classes`, so the bot cannot find one. |
| `items` | Map item id → `{path, name, class, max_stack, durability, fuel_value, weight, category}` for every item a recipe or station references. |
| `players` | `[{name, recipes_unlocked: [recipe ids], not_persisted}]` at generation time: the offline fallback of the unlock mirror. |
| `interaction_ranges` | The detector's `EInteractionDistance` → cm map. |
| `wiki_check` | `{compared, match, qty_mismatch_count, facility_mismatch_count, no_wiki_row, report}` when built with `--wiki-check`. |

Build 26161880: 1232 recipes (954 with inputs; 926 with a station; the rest are journal, quest and vendor-only entries), 45 station types (25 with a loaded actor class and recipes, 8 developer test rows), 1081 items; wiki check: 619 of 739 comparable recipes match exactly (Iron Bar = 3 Iron Ore or 9 Iron Salvage Pile at the Furnace, as on the wiki); the 120 differences are mostly wiki naming (raw vs pristine fish, spelling) plus about 20 quantity changes where the game data is authoritative.

### ../mod/body/recipe_data.lua: what the mod loads

Generated together with the JSON (`--no-lua` skips it; `--lua-only` regenerates only this file from the existing JSON), so the mod never parses 2 MB of JSON. Schema `dw_recipe_data/1`: `recipes[id] = {path, inputs={{item_path, n}}, outputs, stations, t, tmax, qm, pt={min,max}, fuel?, extra?, rep?, uq?}` (`uq` = the unlock query strings of the recipe's progression bundles, e.g. `ALL ITEMS[ Iron Ore ] AND ALL ACTORS[ BP_Station_Smelter_C ]`), `stations[id] = {kind, name, classes, range, rate, fuels={item_path}, vendor}`, `items[item_path] = {id, name, max_stack, durability, fuel}`, `interaction_ranges`, `unlocked_snapshot = {player, ids}`. Test recipes, test stations and stations without recipes are left out. Used by `mod/body/crafting.lua`, the drift check and the client's `client_mod/scripts/crafting.lua`.

## dependencies.json: what the mod and tools depend on

Generated by `.venv\Scripts\python.exe -m tools.patch_pipeline deps` (`tools/patch_pipeline.py`; runbook `docs/RUNBOOK-patch.md`). Lists every `/Script/...` and `/Game/...` path, `Class:Function` pair, `FindAllOf` class name, member name (`.Prop` / `:Func()`), enum and bridge tool name found in `mod/**/*.lua`, `tools/build_catalog.py`, `tools/gen_attack_data.py` and `brain/BRIDGE_PROTOCOL.md`, with the files that use them and a tier (`core`, `tooling`, `debug`). After a patch, `patch_pipeline report <old> <new>` checks each one against the new dump and lists the removed or changed ones as BROKEN.
