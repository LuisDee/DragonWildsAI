# Drain model-queued diagnostic work

## Goal

Make the existing directed survival diagnostic observe the work the model actually queues before taking its final state snapshot. The 528ae99 run selected `run_skill` but the harness returned after `handle_event`; it did not execute the queued goal, so it cannot measure recovery.

## Approach

After review, adapt a private copy of `logs/recovery/survival_diagnostic.py` under `logs/recovery/`; do not change production, judges, or the original helper. Preserve the same plain command, `dev_director` memory, dev guard, Controller-only configuration, existing Capped limits (20 Haiku / 0 Sonnet), $6 total daily guard and no warm-up. After `handle_event`, check the actual `session.agent.pending_goal`. Only while a model-queued goal remains and a monotonic five-minute deadline, call cap and small explicit step-count bound have not been reached, call the existing `session.step()`. Stop immediately once pending work is empty; do not run an idle pump or choose a skill, insert a plan, send hints, or resume parked assisted board jobs. Capture the stop reason and pre/post native evidence separately from model speech. Keep the existing `finally` map flush, final probe, result and session-end reporting, using a new private result path to preserve old evidence.

`Agent.step()` first pumps events, then removes `pending_goal`, `pending_tasks` and `pending_skill` and invokes `run_goal`; that call can block, and the pump can process other events before the queued goal. Therefore a pre-step check is not a strict isolation guarantee and an empty pending slot alone is not proof of successful execution. The single Controller request, Director disabled, step bound and operator monitoring limit exposure; trace actual tool calls, event origins and `run_goal` result. A deadline checked between steps cannot preempt an in-flight skill: the sole live operator must issue normal main-channel body stop at five minutes, allow cleanup, and only terminate the owned process if it remains stuck. Do not claim a hard instantaneous dollar cap or autonomous success from a model claim. Start and end native inventories, vitals including endurance, action results and sleep/rest evidence are required; pre-existing developer fixtures and structures must be disclosed.

The separately reviewed follow-up private clone `survival_diagnostic_pumped_planner4.py` retains the same command, bounds and dev guards but permits up to four total Sonnet planner calls alongside 20 Haiku controller calls. It measures recovery when planning is available. The four requests cover all planner uses, including initial planning, repair, replanning and learning; no particular number of replans is guaranteed. This is a distinct measurement with its own timestamped evidence, unchanged production and judges, and the same assisted-world provenance. Seven targeted checks passed, including a real failed learned-skill replan and the provider wrapper refusing a fifth planner request. The inherited deadline is checked between steps, and the spend reader is asynchronous, so retain external operator monitoring and ample verified budget headroom.
