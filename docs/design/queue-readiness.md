# Queue readiness between watchdog probes (2026-10-27)

## Goal

Allow the single reserved dev client to run meaningful queued checks when the watchdog temporarily reports `ok_unprobed`, while never treating its cached map/pawn as a fresh in-world observation or restarting a bridge merely because that sample was unprobed. Report refusal or uncertainty explicitly.

## Evidence and approach

`tools/client_watchdog.ps1` produces an `in_world` state only from a fresh probe and uses `ok_unprobed` for intermediate status updates; the latter carries cached probe fields. `tools/live_queue.py` currently rejects any non-`in_world` initial status and retries all recovery precheck failures, then unconditionally re-arms. The observed same-PID unprobed period and subsequent in-world probe are documented in private `logs/recovery/readiness-research.txt`. No inference from cached pawn/map is allowed.

Reuse the existing `Runner` and `Env` while holding the existing slot: status-only wait for up to 45 monotonic seconds at a modest interval only when the initial sample is fresh `ok_unprobed` with a positive known PID. Recheck the hold each time. Require the same known PID and fresh `in_world` before running unchanged dev guard and bounded ping; a changed PID is not silently accepted as the same client. Unknown PID, malformed/missing/stale or future-invalid timestamp, paused, menu, down and timeout fail closed; no guard, bridge, fixture, or action runs during the wait. Use wall time only to assess timestamp freshness and a monotonic source for elapsed timeout, logged with the last state and reason. Existing `--if-free` fast path stays nonblocking.

Track the last successfully admitted PID. Recovery uses the same bounded status-only wait on a fresh same-PID `ok_unprobed`: after fresh `in_world`, guard and ping, continue without `bridge_start` or resetting transport. A changed PID goes through the existing bounded watchdog-relaunch recovery, with fresh `in_world`, unchanged dev guard and explicit re-arm only for a confirmed changed identity. Unknown identity fails closed. Failures of guard or ping are not converted into unprobed success or silently retried as one. Hold always interrupts. Preserve the existing input-mode sweep after successful recovery and do not repeat a completed check.

Retain existing initial `bridge_start` pending stronger evidence for safely removing it. At every re-arm inspect both the outer command reply and the nested result: success requires `ok` and `started` explicitly true, never a deferred/refused/missing reply. Reset the transport and ping only after confirmed start; on failure or deferral stop the run, report the specific result, and do not run fixtures or checks. Queue re-arms pass `ARGS.try_once` to an independent `immediate_only` option: it refuses busy or uninspectable state before scheduling any callback, while an idle start retains its normal polling loop. Legacy command callers retain delayed behavior. Never force an in-flight action to reload. No changes to frozen dev guard or judges.

## Principles and acceptance

This is generic scheduling and truthful failure reporting, not language interpretation or a game outcome; real client input, one operator, dev-only checks, world state and frozen judges remain unchanged. No principle exception requested. A fresh-context review is required before implementation.

Offline fake clocks/status sequences must cover same-PID unprobed to ready, no re-arm after recovery, timeout and slot release, hold interruption, stale/missing/paused/menu/unknown PID, changed-PID recovery, guard and ping failure without fixtures/re-arm, outer/nested failure and deferred restart without reset or checks, and normal crash recovery. Check elapsed timeout under wall-clock jumps and preserve nonblocking `--if-free`. Run targeted queue tests only with unique temp and RAM guard, then scheduled full gate and live queue remeasurement on the actual deployed version with unchanged dev guard. This design does not claim the watchdog status alone proves world readiness, and tests do not authorize a second client or live operator.

### Immediate-only restart research and correction

The earlier `no_loop` proposal was rejected: `restart_when_idle` passes its options to `M.start`, whose `no_loop` disables the actual bridge polling loop as well as the retry loop. Call-site audit found `bridge_start.lua`, the explicit force command, and existing Lua tests. `tools/scenario_run.py` prefixes command arguments as lexical `local ARGS`; the command passes `ARGS.try_once` as a separate `immediate_only` option. For immediate-only requests, protect `prev.busy` with `pcall`, refuse missing, broken or unknown results rather than assuming idle, and return before retry scheduling on busy. The idle path uses unchanged `M.start` loop semantics; legacy callers retain their behavior.

Additional web queries: `site:docs.ue4ss.com LoopInGameThreadWithDelay CancelDelayedAction Lua reference`; `site:lua.org manual pcall returns status error`. Opened [UE4SS delayed actions](https://docs.ue4ss.com/dev/lua-api/global-functions/delayedactions.html) and [Lua pcall](https://www.lua.org/manual/5.4/manual.html#pdf-pcall). The documented delayed API is conceptual precedent; actual availability is established only by this runtime and harness. **Adapt** the existing in-function idle decision; do not infer successful scheduling or cancellation. Lua regression must count scheduler calls and prove busy refusal never causes a later restart, while idle success creates a real polling loop.
