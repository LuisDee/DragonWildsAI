# Recipe-specific native ingredient counts: design for review

## Existing path and evidence

`crafting.lua` `context()` calls `api.counts_with_status`, currently `client_bridge.lua` `inventory_view` of `inventory.list` rows. `M.plan` retains each catalog recipe input's full asset path before `item_id` normalization; `M.craft_plan` graph uses the normalized IDs and a cloned `pool.values` plus one global `pool.exact`. Its `observed` assumes nil zero and sets short only if global exact; `M.assess` and actual craft readiness use this context. `mod/body/recipe_data.lua` stores full concrete input/output `UItemData` paths. Preserve that path and verify any normalized-ID mapping is unambiguous: same short name from two distinct full assets cannot share a count silently.

Read-only native control `inventory-scalar-positive-native-20261028.json` verified current metadata `UInventoryComponent:GetNumItemsByData(ItemData: /Script/Dominion.ItemData) -> int`, pure + const + non-Net, Air Rune 231 and Water Rune 560 on player `InventoryComponent`, Stone Axe 0; on loadout Air 231 again. Treat results as component-scoped instantaneous observations, not full container proof. Native `UCraftingUIAPI:SelectRecipe` and `SendCraftRequest` are actual input path; historical dump (`docs/DISCOVERIES.md` client crafting and server signatures) also has `CraftRecipe(... Inventories)` and `GetLinkedInventories`, potentially including nearby storage, but exact current UI composition/linked-storage coverage has not been captured. Therefore a main-component shortage says **short in carried main component**, not guaranteed game-wide craft impossibility. Existing real UI result remains authority. Processing station resources/fuel are separate. Do not invoke a game UI handler or server RPC as a read.

## Minimal change proposed

Reuse/adapt reviewed scalar control guard and existing data graph: collect only concrete unique full ingredient asset paths actually visited by the bounded requested recipe graph (including target item where graph needs its owned count); deduplicate and bound to existing plan limits, not all recipes. Resolve via already-loaded `StaticFindObject`, validate full path, valid `UItemData` class, same local controller/pawn/world/component and function binding immediately before/after protected scalar call; no loading assets, array indexing, grants or mutation. An unloaded/ambiguous asset, failed metadata/call, invalid/non-integer/negative result, changed binding, pause, or resource change detected during read yields `unknown` for that item; never coerce to 0. A fresh result is a count for that exact full asset in main InventoryComponent at that moment, not another field asserting globally exact inventory. Do not sum loadout or personal counts: current native control shows duplicate representations, and neither is verified as an additive craft source.

Adapt `pool` to keep per-item `exact`/`unknown` flags alongside counts; clone flags with branch ledgers. On consuming an item, preserve its status. On branch merges keep the minimum remaining observed count and mark exact only if all alternatives have equal, exact remaining value; unknown or divergent branches remain uncertain. Scalar known zero makes `short` truthful **for carried scope**, while positive >= need establishes main inventory supplies enough at observation time. Unknown remains upper-bound planning and must not become missing input. Preserve existing row counts as lower bounds on lookup failures without overwriting a verified scalar count or double-counting its rows. `M.assess`/action readiness must use per-ingredient evidence, and distinguish carried shortage from unknown linked source / station execution; never advertise an unconditional server failure solely from carried shortage. Retain existing count-status compatibility for legacy callers. Query timing is observational: reflex or replication changes afterward can invalidate readiness; UI/server outcome remains final. No global atomic snapshot or goal predicate changes.

Smallest implementation focus: recipe-planning path and direct craft's input assessment only, not inventory list completeness or all other count consumers. Hook per-item query into the already constructed `context` or graph reader, preserving bounded model-selected recipe/alternative graph and model choices. Existing `craft_plan` schema and user-visible evidence may grow only to expose scope, per-item result and uncertainty. No new service/framework, hardcoded ingredients, phrase rules or UFunction calls with unverified parameter marshalling.

## Bounded integration refinement for review

`context()` currently calls `counts_with_status` and hence `inventory.list` before knowing recipe ingredients. Bench `bench_step` repeatedly calls `api.counts()` for output verification; `produced_total` and processing collection also call it. Adding a native count only after context would therefore still touch the disputed slot traversal. Introduce generic `inventory.count_item(full_asset_path)` returning `observed` or `unknown`, validate current reflected single ItemData argument/int return and pure/const/non-Net metadata, typed loaded asset and world/controller/pawn/main-component identity before and after the call. No fallback to the slot iterator on unknown, no asset load, no count cache across observations. Context for a requested plan or direct craft is lazy; graph's bounded path ledger queries each relevant asset and preserves per-item certainty/provenance through branch cloning/consumption/merge. Full asset identity is authoritative; colliding normalized IDs are unknown, never merged. For a shortage or unknown on main, do not preemptively deny a supported station craft because linked storage is unresolved; preserve existing normal UI action and authoritative result. For bench outputs, capture validated exact output path count immediately before send and sample after, only award a gain if both same-scope counts are known and binding remains valid. For processing output-gain accounting use the same scalar reader; station contents and UI transfer continue through existing paths and report their own unavailability. Preserve no-gain/unknown distinction, do not claim output success from a game result alone. Existing other inventory consumers are outside this wave; no general atomic snapshot or new framework.

Implementation uses `inventory.count_item` and the recipe-specific path. Its output includes observation time, exact asset and controller/pawn/component/world identities; before/after deltas require matching identities. The scalar fake covers valid zero and positive, unloaded asset, metadata, unsafe flags, invalid results, world/controller/component change and pause. Crafting fakes cover per-item unknowns, normalized-ID collision, linked-storage-unknown UI dispatch, and unknown output baseline. Before any live use the changes require cold review, full gate and a developer-driven native remeasurement. Processing still uses the existing inventory list to find a UI-transfer slot; no positive row means an incomplete read reports verification failure, not a claimed shortage. That existing traversal remains a separate native-safety limitation and is not used for scalar planning or output deltas. CPF property flags are unavailable in the documented UE4SS Property API; exact observed parameter shape and function flags do not prove those unavailable flags.

## Review corrections

A bench verdict is usable only for the exact full selected recipe path and requested craft count, with one unambiguous matching event; an unrelated event cannot supply or override the result and a missing identity or duplicate matching event is unconfirmed. A matching verdict plus observed same-binding inventory gain is evidence of the UI job and delta, not proof excluding every possible concurrent source of gain. Unknown native item counts are omitted rather than rendered as zero; per-asset observation records (scope, time, identities) follow the branch ledger. Processing captures its output baseline immediately before starting; incomplete before/after counts produce an explicitly incomplete lower bound and never a claimed zero output. If several recipes are possible, one with established sufficient main-carried inputs may be selected while the others remain alternatives; when more than one is established, or none is established and multiple remain possible, ask rather than assert linked storage cannot provide them. This preserves the existing one-viable and ambiguity behavior without treating main-carried shortage as a global veto.

## Output attribution correction

A matching successful bench verdict reports the confirmed craft-request amount separately from the observed inventory delta. Output count attributed to the request is capped at the catalog output for that amount; a larger delta is flagged as possibly concurrent and never claimed as entirely crafted. For processing, matching observations in the carried inventory, station output and newly observed world actors may represent the same unit after transfer. Aggregate distinct output item identities using the maximum of the separately scoped observed amounts, never their sum; duplicate world actor IDs and unreadable counts remain unknown. The result is a conservative lower bound on matching observations, not proof that each came from this processing job or that the reads were atomic.
