# Manifest argument authority

**Goal:** Calls accepted by the body’s advertised schema retain the model’s selected arguments through validation, including recipe-only crafting and nondefault options. Forwarding an option is not evidence that the game implements it.

**Approach:** In `brain/capabilities.py`, use the manifest entry as the sole validation authority when present. Validate the supplied object without removing nulls, copy it without mutating caller or manifest, add only missing top-level property defaults, and validate the resulting object again. Required fields must be present before defaults are added; invalid defaults fail explicitly instead of producing schema-invalid dispatch. Preserve explicit null exactly when the schema accepts it. Obey the schema’s own `additionalProperties` and other restrictions, rather than imposing an unstated restriction. Use the existing typed-model normalization only when there is no entry for that tool. Discovery registers all manifest entries, including known body tools, and the existing `Capabilities.validate` bound method on the discovered client. In `GameInterface.call`, check that registered authority first, validate again at this public dispatch boundary, then send through a small manifest dispatch method; legacy and mock dispatch without registration remains unchanged. This validates direct callers rather than trusting the Controller, with one shared implementation rather than two schema implementations. No semantic mappings, decision rewriting, new framework or game-side changes.

**Generality and principles:** This adapts the existing schema validator and preserves model choice for any tool or entity. It does not interpret player language, alter real player paths, claim state outcomes, or change ownership. No principle is bent. Defaults are an application policy, not JSON Schema validation itself; revalidation catches incompatible annotations and interactions between defaults and whole-object constraints. Existing callers could rely on legacy coercion or removal of nulls: measure and review failures instead of silently restoring rewriting.

**Acceptance and regression:** Offline contract tests cover craft station/recipe/fuel and recipe-only calls; attack weapon/style/force; gather stumps/style; inventory raw; explicit manifest defaults and constraints (including unknown fields when prohibited); accepted and rejected nulls; invalid and interacting defaults; input/schema nonmutation; and a no-manifest typed fallback. Include held-out synthetic schema cases and check resulting calls match supplied values plus declared defaults. A developer-driven dev-client session should later verify native nondefault options and real outcomes before an unassisted deployment-model test; neither an offline forwarding test nor a model claim proves gameplay support. No provider call or frozen judge edit is required here.

**Integration boundary:** `GameInterface.call` currently applies legacy typed validation again to known body tools, and `BridgeClient.call_raw` recursively removes null dictionary values. For registered manifest dispatch, `BridgeClient` must pass validated args directly to the existing `request` method, preserving nested nulls. Keep legacy `call_raw` behavior. Preserve `get_state` success hooks by sharing its existing hook processing with manifest dispatch; `say` and other tools still use the same request machinery, timeouts, reentrant listeners, and lifecycle. An offline fake-transport regression exercises discovery, Controller validation, `GameInterface.call`, and emitted command args for craft (including recipe-only), attack, gather, inventory and schema-valid nested/null cases; also test direct invalid calls, hooks, timeouts and legacy behavior. Wire-level null preservation does not establish that Lua or native game mechanics support nulls or the advertised options.

**Remaining scope:** Current Controller-created Agent tasks reach Executor without `SkillRegistry.validate`, but the legacy Planner and learned-skill path still use separate typed validation. Full-stack schema authority for those paths remains follow-up work; this repair does not claim to cover them.

## Search record

- Need: preserve the advertised tool input contract while retaining the project’s explicit default behavior.
- Repository: searched `docs/DISCOVERIES.md`, `docs/research/`, and `docs/ARCHITECTURE.md` for manifest, schema, argument, tool contract and Pydantic. The 2026-10-28 Sol audit documents actual craft argument loss and recommends authoritative schemas and native controls.
- Web queries: `JSON Schema specification default keyword annotation validation null defaults`; `Pydantic models extra data ignore documentation`; `Anthropic writing effective tools for agents input schema documentation`.
- Found: JSON Schema’s [annotations documentation](https://json-schema.org/understanding-json-schema/reference/annotations) says default is not inserted during validation and need not itself be valid. [Pydantic models documentation](https://docs.pydantic.dev/latest/concepts/models/#extra-data) describes the extra-data policies, including ignored undeclared fields. [Anthropic’s tool definition documentation](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools) defines tool parameters with an input JSON Schema. These are conceptual/API precedents, not verification of Dragonwilds mechanics.
- Decision: **reuse** installed `jsonschema` and the body’s existing manifest; **adapt** the existing explicit top-level default policy with post-insertion validation; retain legacy Pydantic only for absent entries. Build focused regressions, not a new schema framework.
