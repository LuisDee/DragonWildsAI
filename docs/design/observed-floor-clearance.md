## Source interpretation and geometry impact
Epic 5.5 distinguishes sweep FloorDist from fallback-line LineDist. A line result can establish walkability after the sweep did not. `ComputeFloorDist` describes different reference distances for the capsule sweep and bottom-to-floor line. `AdjustFloorHeight` maintains a small offset but its public description does not impose a universal 5 cm admission bound. The old engine-code gist found during research has special handling when a small sweep distance coexists with a larger line distance; that is explanatory precedent, **not verified UE 5.6.1 runtime implementation**. The 5.5 GetDistanceToFloor method page could not be retrieved; no reflected method invocation is proposed.

The current local chain is coupled:

- `walk_sense.clearance` selects `bLineTrace ? LineDist : FloorDist`, then rejects a selected value outside 0..5 cm. Both acquisition and later binding checks use it.
- `walk_guard` subtracts half-height **and this gap** to construct start/target feet.
- `sampled_ground_walk` independently requires `abs(start-floor distance)<=5`. For later samples it computes centre Z as `query_origin.Z - selected_distance + gap`; its target support test also uses `target_feet.Z + half_height + gap`. Step-height bounds and full-shape sweeps then constrain those centres.

Changing only admission leaves a second rejection. Replacing LineDist by FloorDist would shift proposed centres/support references by about 5.882 cm in this example and could change step/ceiling/floor geometry. Raising 5, clamping distance, or treating native grounded status as corridor clearance is not justified.

## Minimal generic repair proposed for review
The correlated diagnostic now supports replacing the universal small-distance assumption with an **observed start-support consistency contract**, in one coordinated sensor/sampler change:

1. Keep selecting the native distance by the valid line/sweep flag. In sensor acquisition and subsequent validity checks, require valid blocking/walkable typed fields, finite nonnegative selected distance and the existing step-derived geometry bound `gap < step_cm - 5`; remove the independent `gap<=5` assumption. Here 6.1427994 is below the unchanged 40 cm bound. Keep both native distances and the selected query kind as sourced diagnostic metadata. Do not clamp, switch to FloorDist, or reinterpret this offset as a new movement capability.
2. Pass the captured selected offset/reference with the sensor shape into the existing sampler. `clearance_line_trace` is an explicitly required boolean in production and every standalone/fake constructor; missing kind never defaults to sweep. At its start query, retain all correlation, walkability and nonpenetration checks and require the same distance-reference kind. The fresh start distance must itself be finite, nonnegative and `<step_cm-5`, even when its residual would be small. Use `abs(fresh_start_distance - captured_gap) <= 5` as the existing 5 cm *consistency tolerance*, rather than requiring the absolute floor distance itself to be <=5. This does not increase the number: it changes the invariant from an untrue universal clearance bound to agreement with the native observed baseline. The measured a830 residual is exactly zero. A changed line/sweep reference or inconsistent offset returns a specific unknown result and requires fresh acquisition; do not infer equivalence between the two numbers. Later raised-query distance checks retain their existing separate semantics.
3. Keep `start_feet`, resolved centre and target-support formulas on that same captured offset. At the starting pose, subtracting and adding the matching 6.1427994 cm cancels coherently; substituting 0.2608275 cm would not. Preserve all existing query budgets, step-height limits and full-capsule overlap/sweeps. Sensor acquisition alone is never a clear corridor or successful go_to.

The consistency tolerance remains an existing conservative policy, not an Epic guarantee. Negative controls below must distinguish changed support from the valid larger line distance. No new floor queries are added to the frame-rate validity check by this proposal.

**Same-lease validity:** capture the selected distance/reference once per successful sensor lease. Each existing `stable`/validity read must still validate the current native fields against that capture: unchanged reference kind, finite nonnegative distance within the step-derived bound and a distance residual within the same 5 cm tolerance. If it changes beyond that contract, permanently invalidate the lease and its sampled/cache evidence, release through the existing cleanup path and require a fresh acquisition. Never silently refresh `shape.clearance_cm` while an existing scan uses the old geometry. A legitimate line-to-sweep transition may therefore cause conservative reacquisition; staged developer validation must measure this rather than treating it as a newly impossible route. Existing lifecycle/identity/pause/owner/pose-drift/TTL rules remain independent requirements.

**Negative values and capsule geometry:** preserve rejection of a negative selected gap, nonfinite/missing fields, `step<=5`, `gap>=step-5`, nonpositive radius, half-height smaller than radius, changed dimensions/profile/step, or ignored collision actors/components. Do not apply abs/clamp or switch distance fields to make these pass. Radius is a real full-capsule sweep dimension, not a replacement floor-distance threshold; a line support hit does not prove side/ceiling clearance for the radius-34/half-height-88 capsule. Sampler floor penetration/nonwalkability and existing negative resolved-query-distance checks still stop/return unknown under their current semantics. Unknown typed fields, correlation/query errors, callback cardinality or cleanup failures remain unknown; no movement follows from acquisition-error handling.

If the query disagrees with cached CurrentFloor, changes kind/reference, is nonwalkable, penetrating or uncorrelated, do not authorize movement. Record the discrepancy and choose the smallest next support observation. A line fallback beside a capsule-side obstruction may be legitimate native grounding without making an adjacent full-capsule chord clear. Initial overlap approximation, full-shape sweeps, step limits, lifecycle/freshness/ownership and all existing budgets must remain.

Narrow observability can accompany a later reviewed repair: preserve a structured acquisition stage/reason with these bounded known numeric/flag observations through walk_guard's `sensor_unavailable` packet. Currently `pcall(acquire,alive)` captures only its first result and loses the returned reason. Use explicit known reason codes; do not expose arbitrary exception strings, paths or raw UObject data to models. Any actual behavior repair would be confined to the sensor/sampler/guard contract plus focused tests, with ownership assigned by root; none is implemented here.
