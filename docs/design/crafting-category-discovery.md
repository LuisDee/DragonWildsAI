# Crafting category discovery (2026-10-27)

## Goal and evidence

When a model requests a craftable category rather than an exact output name, provide truthful candidate item identities from game catalog data so it can choose a specific item and investigate the recipe. In the current live run `craft_plan("Hatchet")` twice returned `unknown_recipe` with no candidates; the model did not call `recipes` or `lookup`. The catalog's Stone Logging Axe entry carries category `Item.Equipment.Tool.Hatchet` and is a recipe output. This explains a plausible discovery gap; it does not establish that the recipe is currently unlocked, its station exists, or it can be crafted in this world.

## Approach

Preserve existing exact ID, path and display-name matching, then existing unique or ambiguous literal name/ID substring results. Only if there are zero name/ID matches, compare the normalized query for equality with an item's complete catalog category tag or its final dot-separated component, over craftable recipe outputs. Do not turn a category match into an automatically selected item, even when there is exactly one: return `ambiguous_target` with a candidate containing the actual item ID, display name and source category, and a truthful prompt to choose an item. Multiple results are sorted deterministically and bounded using the existing response limit; include a total/truncation indicator if results exceed the limit. Missing category data is not invented, an empty category match remains `unknown_recipe`, and category substring or synonym expansion is out of scope. The model may then call an existing recipe or planning tool for an explicit item; planning and crafting never run as a consequence of category discovery alone. The same behavior must apply consistently to `recipes`, `craft_plan` and `craft` through their shared resolver, with wording for one versus several candidates that does not claim several matches when only one exists.

The initial assumption that the Lua catalog already contains categories is incorrect: `client_mod/scripts/crafting.lua` reads generated `mod/body/recipe_data.lua`, whose Stone Logging Axe row has ID and name but **no category**. `data/recipes_26161880.json` has the category and `tools/build_recipes.py` retains it in JSON, but `lua_data()` drops it. The minimal implementation therefore also forwards optional `category` through the existing generator, regenerates the Lua data from the existing checked-in catalog without live extraction, and adds a generator regression. Proposed ownership: `tools/build_recipes.py`, `mod/body/recipe_data.lua`, `tests/test_recipes.py`, `client_mod/scripts/crafting.lua`, and `client_mod/tests/test_crafting.lua`; no changes to source JSON or game state. Missing category fields stay absent rather than acquiring inferred values. Fresh-context review and explicit ownership assignment are required before edits.

## Principles and acceptance

The category is factual metadata, not a phrase-to-action rule, hard-coded entity list or model decision. This adds discovery only; the game client retains its real input path and observed outcomes. No principle exception requested.

Offline tests: verify optional category survives JSON-to-Lua generation; test exact ID/name and existing substring precedence; category full-tag and leaf matches, single and multiple candidates, deterministic limits, absent category and no match; held-out categories and case/whitespace normalization; confirm all three consumer tools return candidates without invoking crafting and that an explicit chosen item still plans normally. Then run the relevant targeted Lua and generator tests and design-note check, followed by the scheduled full gate. On the single dev client, live validation must capture the new tool response and actual model-selected follow-up, then separately verify any crafted result in game state; candidate discovery alone is not proof of an unlocked or completed craft.
