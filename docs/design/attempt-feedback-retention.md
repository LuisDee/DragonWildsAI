## Source cause and priority
`Director._run` already retains `(step.actions + board_recs)[-40:]`, but overwrites `_last_results[step.id]` with `_result_summaries(board_recs)` from only the latest run. Empty input therefore replaces earlier failures with `[]`. `_fail_attempt` copies that empty cache, and `_messages` does not separately serialize the saved `step.actions`. The decisive repair is the current-attempt evidence source, not a perception rewrite.

Two adjacent boundaries affect the same proof: `_run_with_first_call` hand-selects a small `data` whitelist, removing route_feedback before Controller call 16; `_result_summaries` drops already-recorded arguments and provenance fields. Missing action IDs/timestamps are a separate capture limitation: raw executor logs have task IDs/time, but the current Agent directed records do not carry them. This wave must not invent those values or turn missing metadata capture into a platform project.

## Smallest implementation proposal
After fresh review and explicit implementation release, own `brain/director.py`, one focused regression file and this note. No Agent, Executor, body, board schema, storage migration or research-tool execution changes are required for the verified overwrite repair.

1. Feed the existing bounded `_result_summaries` from `step.actions` after appending this run's records, rather than from `board_recs`. Preserve the current 40-record step bound, last-eight summary selection and failure-first data allocation. An empty/read-only/refused run contributes no fabricated body action and cannot erase prior results from the same attempt.
2. Clear `_last_results[step.id]` when Director activates a pending step. `BoardOps.activate` already increments the attempt and clears `step.actions`; reuse that lifecycle without editing it. Clear/rebuild the cache before the new attempt's Controller event. Existing completion/task-end cleanup remains. Repeated runs within one attempt retain feedback; a new attempt, including one reusing the same step ID, must not inherit it as fresh evidence.
3. Use the same summary formatter for `first_call_result`, retaining bounded `data` instead of its separate whitelist. Keep existing `first_call_result`, `last_results` and `last_actions` field names. Preserve already-recorded `args` and `origin`, and copy optional identity/source/time metadata only when the input record actually supplies it. Keep first-call execution, tool selection, predicates, failure counters and model decisions unchanged.
4. Supply board task ID, step ID and attempt alongside the feedback in Controller events and Director failed-step detail, derived from the current board context. This is attempt correlation, not an invented executor action ID. Both models must be able to distinguish the current observation snapshot from earlier action results.

No new action/refusal collection, global logging framework or route policy is part of this proposal. A refused Controller call remains distinct from an executed body action; its existing correlated tool-result message is not promoted into physical effects or learned successful actions.

## Metadata and freshness contract
| Evidence | Current availability | Treatment |
|---|---|---|
| Tool, args, ok/reason, result data, origin | Present in directed body-action records | Retain bounded copies through the common formatter. Args mean the submitted arguments recorded there; a native resolved/requested target in result data remains separate. |
| Board task/step ID and attempt | Available at the Director boundary | Include as surrounding feedback context; preserve the original attempt across later prompt composition. |
| Native generation, supplied sample timestamps, partial/unknown flags | Available only when supplied inside result data | Preserve verbatim within the existing bounded data contract, with explicit truncation/omission markers. Do not infer missing native facts. |
| Executor action/task ID, provider tool-call ID | Raw logs or ordinary Controller tool messages have some IDs; directed records generally omit them | Copy optional supplied values without conflating these different IDs. Missing values remain unknown; do not synthesize an action ID from the board step or claim raw-log correlation already reaches Sonnet. |
| Action completion/receipt timestamp and source | Generally absent in current directed records | Preserve supplied values and their stated semantics. Otherwise report/describe freshness as unknown. A current snapshot time or prompt creation time must never become the old action's observation time. |

The existing eight-summary/16 KiB total and 8 KiB per-result-data limits remain. Reserve small correlation fields before bulk argument/data arrays; added args/metadata share a 1 KiB per-summary reservation so they cannot monopolize the data allocation or bypass the total cap. Mark omissions and truncation without cutting serialized JSON. Do not replay all raw logs into prompts or expand selection beyond the existing last-eight policy. Earlier results are retained evidence from the same attempt, not claims that the world remains unchanged.

New capture of missing executor action IDs or actual receipt timestamps would require a separately reviewed small Agent/Executor boundary change. It is not a prerequisite for proving this minimal loss repair and is not claimed complete by it. Raw executor/bridge/provider logs remain intact for developer correlation.

## Principles review
This is generic evidence preservation: arbitrary primitive results and arguments survive the same boundaries, regardless of task wording, item or place. It changes neither the selected action nor game state, and it does not weaken predicates, milestone definitions or judges. Existing result bounds limit prompt growth. The model still chooses its response to a truthful failure. No completion can be inferred from an error summary, a model claim or an offline replay.
