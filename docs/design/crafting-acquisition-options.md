# Craft planning: acquisition alternatives and inventory uncertainty

## Evidence and root cause

The 2026-10-28 `tree_gap_7c819a7c6b68` pilot used six Haiku calls and no planner calls. It tried a chop, received `wrong_tool`, requested an explicit item plan, then tried three remembered graves and asked for supplies; it did **not** call inventory. This is an observed sequence, not proof why the model made any choice or that prompt compaction caused the decision.

Its raw `craft_plan` response for the chosen item describes a nearby station and inputs of six stone and eight ash logs, but expands two catalog `DA_Recipe_Vendor_*` recipes, yielding two currency leaves totaling 42, two merchant-finding steps, and two `craft` steps. `gather_instead` exists only deep in each chosen node; the flattened `missing` and `steps` present the vendor branch as if mandatory. Source evidence: `crafting.lua:M.assess` tests missing inputs before checking a nearby station; `RANK` prefers `missing_input` over `no_station`, and `plan_tree.node` selects `cands[1]` whenever its status is `ready` or `missing_input` even when a gather profile exists. Expansion reassesses with an empty pool and turns the selected path into `no_station` and `find_station` plus `craft`. `W.gather_for` chooses only the first alphabetically named profile per item. The catalog's merchant station `UmS_Merchant_Smith` has `kind=crafting`, empty class names and no native vendor flag in the JSON; the generated data is thus not sufficient to treat its recipe as a verified ordinary crafting station or silently assume vendor capability. Do not infer vendor semantics solely from an ID prefix. Existing tests at `client_mod/tests/test_crafting.lua:243-294` cover one gather branch, ranked alternatives and a cycle but the gather fixture unlocks only the root, so it does not exercise an unlocked competing purchase recipe.

Separately, `client_bridge.lua:965` gets only the first return from `inventory_view`, and `crafting.lua:context` receives `api.counts()` without read completeness. `M.assess` and `plan_tree` substitute zero for absent keys. A partial inventory read supports observed counts as lower bounds, not zero absence; therefore the pilot's `have=0` values do not prove empty hands or missing materials. This is a distinct evidence defect, not proof that the model lacked those items.

## Proposed bounded change for fresh review

Reuse the existing `craft_plan`, recipe catalog, `gather_profiles`, station census, unlock facts and shared carried-pool arithmetic. Present each ingredient as an **AND** requirement of its selected recipe and each acquisition as explicitly **OR** alternatives with typed origin/provenance: observed carried lower bound, candidate gather profiles, explicit recipe options with real ingredient and station facts, and vendor only when separately identified by trustworthy catalog/native metadata. Profile membership is a capability hint, not a claim of a nearby resource, tool, route, unlocked recipe, reachable merchant, or guaranteed yield. Include output count/crafts and station candidates, with unknown identity/type/availability stated as unknown. Show all matching profile resource names, deterministic and bounded, not just first; do not hard-code an item, station, synonym, plan, or developer-directed action.

Do not flatten one chosen acquisition into **unconditional** root `missing` or `steps` when a node has unresolved alternatives. Preserve compatibility for a single unambiguous branch where it is valid, and either attach steps/missing to their own recipe branch or label the existing chosen branch as conditional plus expose explicit alternatives; report branch totals and truncation if capped. Never label a vendor-like catalog entry as executable craft merely because `kind` says crafting; if vendor identity is unknown, retain its exact recipe/station metadata and unknown capability instead of silently classifying. Native craft outcomes, unlock and station checks remain authoritative. The model chooses which real tool to invoke; no automatic execution or scripted solution. Explore stations' own build requirements by returning existing recipe/catalog facts or a separate existing lookup result, not by inventing station placement instructions; if station identity has no mapped recipe, say unknown rather than promise buildability. Detailed exact output fields and compatibility must be decided by the independent reviewer before implementation.

Supply counts **and** carried `read_status` from the same existing `inventory.list` snapshot, reusing `inventory_view` and propagating its status through a backward-compatible optional second return or a dedicated read-only accessor; changing the shared bridge API requires explicit owner review. `have` is the observed lower bound. If known count already meets a need, it proves enough for that snapshot; when incomplete and below need, shortage is **unknown**, not definite missing. A computed difference may only be labeled an upper bound on additional need. Partial/unknown cannot produce a definitive `missing_materials`, `ready=false` solely on assumed zero, or a finished plan; complete exact reads preserve current arithmetic. Do not weaken actual craft execution gates: distinguish read-only planning evidence from native authoritative execution results. This contract must cover both `M.assess` output and `plan_tree`; other count-sensitive consumers are separate scope.

Keep branch arithmetic correct: one shared pool for required ingredients of the **same** selected recipe, but independent copied pools for alternatives so exploring one does not consume resources of a mutually exclusive branch. Preserve cycle/depth guards, configurable count limits and a bounded node/alternative budget with explicit totals/truncation, so data expansion cannot explode. Multiple ingredients share counts without double spending; insufficient observations never become exact deficits. Do not combine alternative ingredient options with AND, or infer OR within a recipe if the catalog encodes required inputs together.

## Reviewed implementation contract

Each requirement has observed_have, exact/lower_bound semantics and enough/short/unknown sufficiency. Acquisition options are OR branches; each recipe's inputs are AND requirements. Branch pools are cloned, then only the guaranteed minimum remaining across branches is exposed downstream; disagreement marks allocation semantics lower-bound. Truncated alternatives invalidate exact allocation. Counts and status come from one read-only bridge snapshot through a new accessor; existing counts and native action gates are preserved. Flat legacy steps and missing are omitted when choices or observed insufficiency are unknown. Recipe IDs and station metadata are facts; non-vendor metadata does not establish execution capability.

A node with exactly one acquisition is represented directly by that node (and `options_total=1`), retaining legacy readable fields without duplicating recursive inputs in the serialized wire. Nodes with multiple acquisitions expose `options` as OR alternatives; pinned roots retain their nested input alternatives.

Craft-plan station kind and proximity plus sufficient inputs do not establish executable capability. A proposed craft is explicitly conditional with unknown capability; `ready=true` is reserved for an already observed sufficient item. This uncertainty applies to `craft_plan` only: legacy `recipes`/craftable assessment and actual native craft gates remain separate and are not claimed fixed by this wave.
The serialized `ready` field is absent when execution capability is unknown; `choices_unresolved` denotes actual multiple or truncated alternatives, rather than inventory or execution uncertainty alone.
