# Craft-plan requested quantity semantics: private design for review

## Evidence and present contract

The fresh `no-axe-pilot-20261028-105806-bf394f01.json` used the now-visible unlocked recipe, then `craft_plan(item=StoneLoggingAxe,count=1)` returned root already held; the controller used its old axe. Native wood and XP increased, but there was no observed craft/build and no evidence that a new axe was produced. This is not a GOAL craft pass. No model instruction, inventory rewrite or item-specific workaround follows from it.

`crafting.lua` `M.plan_tree` currently calls `observed(pool,item,need)` for the root item and returns `have` when inventory meets it. A pinned recipe already avoids consuming the root inventory (`snapshot=clone(pool)`, `remaining=need`) and expands that recipe. Direct `craft` `resolve_candidates` interprets item count as additional output items (rounds up each recipe's yield); `recipe` count is craft operations. Manifest currently describes `craft_plan` as a dependency plan but does not clearly distinguish desired new output from inventory target. A model cannot infer the missing distinction from tool result alone.

## Narrow proposal

Offer explicit generic enum `quantity_mode`: `additional_output` (plan new production; default for the public `craft_plan` tool to align its counterpart `craft`) and `inventory_target` (plan enough holdings to reach a final target). Publish the default and both choices in the tool schema/description, echo mode and count units in every successful result; reject invalid values with `invalid_args`. Preserve `M.plan_tree` pure callers' existing inventory-target default for compatibility: `plan_tool` explicitly passes its public default. This is a conscious behavior change to the public default, so independently review the manifest, call sites and regression evidence; an explicit-only mode preserving the old public default is lower compatibility risk but would leave ordinary tool calls ambiguous unless models select it. No parsing or rewriting user wording, automatic craft dispatch or special item rules.

For an item root in `additional_output`, inspect the root on a clone exactly like existing pinned-recipe behavior: report true observed count, asset/scope/uncertainty and timestamp as observation; allocate **zero** of it toward satisfying this requested new-output root; do not mark root complete just because stock exists. Expand the model-chosen/resolved item into its normal recipe/gather alternatives for the full requested new quantity, retaining cycles, unlock/station uncertainty, truncation and conditional execution. `observed_have` is the actual observed count or unknown, not fabricated zero; a distinct `allocated_from_inventory=0` and `requested_additional_output=count` explain the calculation. Do not spend the cloned root observation in the main pool: descendant ingredients still use and allocate their own observed inventories exactly once under the existing branch ledger. When the root item itself appears as a descendant, retain existing cycle handling; do not invent stock or recursive execution. A missing/unloaded root count remains unknown as an observation but does not change the explicitly requested additional amount. For `inventory_target`, preserve current root allocation, status, net shortfall and readiness exactly. The API should not turn unknown ingredient counts into zero or unconditional shortages.

For a pinned `recipe`, count remains number of crafts, as in direct craft; output quantity derives from the recipe yield, and additional mode retains existing behavior. Do not silently reinterpret recipe count as produced item count. Explicitly document/test `inventory_target` with `recipe`: either reject this contradictory combination with a clear `invalid_args`, or support it only with an unambiguous separately specified unit; recommend rejection rather than silently overriding the pinned craft request. For `item`, count means output units; round each selected recipe up by its output yield, report requested output and predicted produced amount separately, and preserve overproduction/alternatives as planned quantities, never proof of execution.

`ready` must not become true merely due to pre-existing root holdings in additional mode; sufficient ingredients still yield existing `execution_unknown` conditional suggestion, not a successful craft. If inputs or station/unlock are unknown preserve uncertainty. The resulting plan is information only; actual UI craft action and independent game state remain authority. No changes to frozen judges, prompt phrasing, per-world memory, source inventory, or actual character action are part of the design.

## Acceptance and measurement

Actual module fakes: one owned root plus request one additional => observed one, allocated zero, root expands one craft and inputs, never root `have`; root unknown => unknown observation and same requested amount, never synthetic zero; input stock reused with exact provenance; `inventory_target` one owned => existing `have` and compatibility; requested item yield >1 rounding; pinned recipe count equals craft operations and incompatible mode response explicit; same item as descendant/cycle, multiple alternatives, unknown ingredients, branch conservation and budget bounds; manifest enum/default and bridge serialization; no model-chosen tool or predicate rewritten. Existing tests retain pure defaults. After targeted regression/full gate and developer-driven real-UI validation, perform fresh ordinary unassisted deployment-model observation with before/after native craft result, item delta and XP; a controller may choose another method and that remains truthful, not forced.

## Implementation and caller audit

The public body manifest and Director proxy schema expose the same enum and `additional_output` default. The mock GearWorld follows the same item-mode distinction; stock-target test callers in `tests/test_director_velgar.py` now explicitly choose `inventory_target`. Other production references are descriptive or generic proxy dispatch, not hard-coded stock-target calls. Frozen `evals/fixtures/voice_manifest.json` retains its historical schema and was not modified. For the pure `M.plan_tree` API, omitted mode retains the preexisting item-stock behavior and the preexisting pinned-recipe additional-crafts behavior. Explicit stock-target mode paired with a recipe is rejected at the public boundary. A root inventory observation is separate from the zero allocation for new production; original stock stays available to descendants, including a legitimately consumed same-item descendant, with cycle checks remaining in force.
