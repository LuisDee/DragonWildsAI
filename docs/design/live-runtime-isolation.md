# Stable live runtime and candidate worktree (2026-10-27)

## Goal

Keep the single dev client and its companion available for meaningful queued live validation while candidate changes are developed and tested elsewhere. Integration briefly interrupts that lane only at a verified safe boundary. This is a proposal for fresh-context review, not an implemented deployment protocol.

## Current evidence and constraints

The installed UE4SS `DWClient/scripts/main.lua` defaults `DW_CLIENT_ROOT` to `C:/gameserver`; it loads the bridge from that root. `client_bridge.lua` rereads module contents and reloads changed modules independently. `tools/config.ps1` instead derives `$RepoRoot` from its own checkout. `tools/install_client_ue4ss.ps1` copies the mod, and the architecture notes say a changed installed `main.lua` requires redeployment and a client restart. Consequently editing the deployed tree can affect a running client before tests finish, and a file-by-file copy is not an atomic release.

`bridge_start.lua` uses `restart_when_idle`; `busy()` checks the action slot, waiters and unread brain/debug bytes. It is not an admission lock: a new command, combat/reflex or fed verification can arise immediately after the check. It also does not by itself prevent module hot reload during a copy. `M.stop()` cancels the bridge loop, but this alone is not evidence that all separately scheduled service callbacks, combat, input and pending verifications are quiescent. Do not rely on a hold file, a Git checkout, a directory junction swap, or a single `busy()` reading as proof of safe publication.

`brain/run_live.py:code_version` identifies the brain checkout; `evals/bench/hashes.py` hashes Git HEAD plus a dirty marker, with body and companion paths and frozen `JUDGE_PATHS`. These are not byte attestations of independently copied or already-loaded Lua. A candidate worktree's hashes must never be used to label a live session running different deployed files. No judge change is proposed.

## Approach and file/path plan

1. Retain `C:/gameserver` as the deployed Git checkout, runtime root, queue and state owner. Develop in one managed linked worktree rooted outside it, at a path returned by the worktree manager. One owner integrates; no competing live tester, brain, server or new port. Existing client slot and live queue remain the scheduling authority. Keep deployed code unchanged during candidate editing and tests.
2. Candidate tests run with the candidate as working directory and import root. `tools/check_all.ps1` changes to its own checkout and invokes its local `.venv`; provision a candidate environment from the project's declared dependencies, or explicitly use the existing interpreter without changing its packages only after proving interpreter, Python imports and Lua loads execute actual candidate files using a distinctive candidate-only sentinel and isolated outputs. Do not copy a virtual environment or install into the live one during play. Inventory ignored requirements first: `data/wiki/knowledge.sqlite` and generated catalog/index inputs may be required by specific tests; use a read-only snapshot of ignored wiki/SQLite data where justified, never a writable live index or junction to live state. Missing data is a visible blocker, not a skipped passing gate.
3. Audit path resolution before trusting tests. Lua suites commonly derive root from their file path, but `main.lua`/`client_bridge.lua` default to `C:/gameserver`, and `tools/combat_s1.py` embeds that path in Lua commands; it is a live tool, not evidence for candidate offline tests. Search literal paths, environment overrides, subprocess working directories and Lua harness `REPO` setup across tests and tools; instrument representative Python imports and Lua loads to prove they resolve to candidate files, and test with a deliberately distinguishable candidate-only fixture. Historical fixture log strings are data, not execution paths. Run tests with isolated temp/output directories, no live `client_io`, `logs/state`, world memory or secrets. Audit beyond the literals before declaring coverage complete.
4. **Phase 1: client-off integration.** Once the candidate is reviewed, committed and tested, the live operator reserves and renews the existing slot, preserves the queue, stops admitting new live checks and brain work, and drains accepted work, including persistent follow and callbacks. Check action, waiters, unread commands, arbiter/movement, fight and fed/reflex pending state; defer if work remains or its state is unknown. Announce the client stop/restart, use the existing verified normal stop procedure and hold the watchdog against automatic relaunch, stop the owned brain so it cannot read changing files, and verify their actual process state before changing any files. A hold alone is not the publication barrier; verified client process absence is. Keep the server, Steam and world/state intact.
5. Preflight a clean original index and tracked worktree, verify the prior runtime HEAD is an ancestor of the exact tested candidate commit, and check untracked and ignored paths for collisions with every added, changed or deleted path. If any condition fails, defer; rebase and review/retest offline where appropriate. Integrate with `--ff-only` to that exact commit and verify resulting HEAD, never overwriting pre-existing user changes. Record prior HEAD and a byte-verified manifest/backup of affected paths, including absent/present status for additions and deletions and the installed entry point, plus candidate commit and published manifest. Preserve untracked/ignored data and all state; never reset, restore, clean or checkout over the shared working tree. With the client absent verify the whole set and installed entry point. On error retain the hold. Rollback is a non-destructive forward revert of exactly the integrated candidate commits, or a reviewed and verified equivalent, while the client remains absent; record the **new actual rollback HEAD**, and prove affected code bytes and added/deleted path presence match the prior manifest. Do not claim the old SHA or rewind world progress. On conflict or uncertain identity stay held and defer.
6. Relaunch via the existing dev-target lifecycle, verifying effective loopback dev and forbidden Shockbyte, loaded bridge instance and services; start the single brain from the deployed checkout when appropriate. Record runtime HEAD, dirty state, deployed and installed-entry hashes, body/companion/judge hashes, game build and bridge start identity with each measurement; if identities differ or are unknown, do not attribute a benchmark to the candidate. Changes to installed `main.lua` or process-loaded watchdog scripts require their documented redeployment/restart. Never restart Steam as routine repair. Release the hold and slot only in the order required by the normal lifecycle, after verification; failed recovery remains held and uses verified rollback.

**Phase 2, optional:** Only if shorter interruption is worth the complexity, design and prove an admission/quiescence and publication mechanism at the bridge/loader boundary. It must stop new brain/debug admissions, drain accepted work and verify all the pending states above plus separately scheduled callbacks. It must prevent every reader from observing partially published modules, including `mod/scripts`, and fail closed on interruption. A staged directory, per-file rename or idle snapshot alone is insufficient. Do not treat Phase 2 as a prerequisite for Phase 1.

Before live work confirm effective target is loopback dev, Shockbyte is forbidden, and existing process/lease/hold/slot state. A separate live queue/operator owns the single client and schedules meaningful checks against the deployed version while analysis and candidate development proceed; only the reservation owner acts. Schedule integration, full gate or a benchmark batch as short windows and resume queue afterward. Full gate and benchmark batches obey the one-heavy-workload rule; do not keep the client off throughout coding. On the 8 GB host, observe available RAM and commit headroom, pause new heavy work at the existing 350 MB critical guard and follow the repeated-critical policy. A normally running client/brain is distinct from a benchmark batch or world load. Record active, idle and blocked time with reasons and version, without claiming a duty cycle or throughput until measured; investigate app memory independently.

## Candidate offline test path selection (2026-10-27)

**Goal:** Candidate offline test results must exercise candidate Python and nested Lua sources, with temporary outputs, while the deployed runtime stays available. This is test-path selection, not proof of deployment isolation or the full gate.

Tests that explicitly exercise alternate roots may still override it locally. `tools/check_all.ps1` accepts an optional explicit Python interpreter while retaining the local virtual environment default and checkout working directory. **Precedent and search record:** Searched repository `docs/DISCOVERIES.md`, `docs/research/`, `docs/ARCHITECTURE.md`, tests, Lua loaders and gate. **Acceptance:** A Python import and real nested Lua `loadfile` must resolve to the current checkout and a candidate-only sentinel, including with a stale inherited root; an isolated temporary output is used. Run targeted tests and design-note checks with unique temporary roots when RAM permits. Audit explicit subprocess environment replacements and literal runtime paths; report unresolved risks rather than claiming full isolation. The full gate and live validation remain separate scheduled work.
