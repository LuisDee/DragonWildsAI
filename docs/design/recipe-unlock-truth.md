# Recipe unlock evidence and prerequisites (2026-10-27)

## Goal and observed evidence

When a recipe cannot be crafted, distinguish an actually locked recipe from unreadable unlock state and give the model truthful prerequisite information without performing the prerequisites for it. On the current dev character, a Crafting Table actor was observed after construction and Construction XP increased from 36 to 48; the character carried eight ash logs and six stone. Repeated Stone Logging Axe craft attempts returned `not_unlocked`. This establishes the reported symptom, not whether the native recipe was genuinely locked or what action unlocks it.

The separately owned read-only probe (`logs/recovery/progress-diagnostic-cde.txt` and `progress-native-cde2.json`) returned native `IsRecipeUnlocked` boolean **false** for the target; the persistent set contained 83 recipes and did not contain it, and the ephemeral set was empty. Native `HasPickedUpItem` returned true for both ash and stone using actual enumerated item objects. `ActorsInteractedWith` contained five classes but no Crafting Table class, while a built table actor existed. Inventory and skill XP were unchanged across the probe. `HasInteractedWithActor` was not called because its const-reference ABI was not verified. These observations establish the native lock at that moment and make missing recorded interaction consistent with the condition; they do not prove that interacting will unlock this recipe. An older `docs/DISCOVERIES.md` statement that holding an item and being near a station unlocks most recipes is not demonstrated and must not be treated as proof. Do not force an unlock, bypass native checks, grant items, or hard-code any particular recipe or station.

## Source and dump audit

`client_mod/scripts/crafting.lua` `W.unlocked` reads only `pc.ProgressComponent.RecipesUnlocked`; an empty set or failed iteration becomes unknown. Its `M.assess` distinguishes missing table from a known recipe absent in the read set, but `plan_tree` maps `unlock_unknown` to a `not_unlocked` node, conflating uncertainty with an actual lock. The generated `uq` stores progression query strings and `unlock_text` currently joins bundles with OR while replacing station classes with names; the cross-bundle relation is unverified. `brain/knowledge.py` has a separate text renderer and uses only `unlock[0]`, losing other bundles. Preserve each raw query separately, including its within-query ANY/ALL/AND/OR operators, and label the relation between bundles unknown until verified rather than joining them logically.

The current JSON catalog contains 21 recipes with more than one nonempty unlock bundle query; this count shows the first-only renderer has real coverage implications, but does not independently prove the semantics of combining those bundles. The local CXX header dump declares `RecipesUnlockedThatShouldNotPersist`, `RecipesUnlocked`, `ItemsPickedUp`, `ActorsInteractedWith`, and named `IsRecipeUnlocked`, `HasInteractedWithActor`, `HasPickedUpItem` methods. The dump reports the listed methods as `void`, which does not prove their reflected return values or callable Lua ABI. `ERecipeUnlockType` has `None`, `ItemFirstPickup` and `Interaction`; these declarations support investigation, not a conclusion that proximity, ownership, or a specific interaction satisfies the target recipe. Compare each candidate native query and the sets against game/UI behavior on the same dev character before using it as authoritative; validate return types and failure modes in this installed build. No method must be invoked merely because its name sounds read-only.

## Minimal design for review

Retain the actual `not_unlocked` result; this evidence does not justify changing or bypassing the unlock reader. Correct `plan_tree` so unreadable unlock state remains `unlock_unknown` rather than `not_unlocked`. Expose all raw catalog condition strings unchanged as separate source facts in both crafting and knowledge outputs; any class-name-rendered version is additional and must not replace the raw expression. Explain generically that player progression separately records item first pickups and actor interactions, as supported by the reflected enum and observed sets; present this as contextual evidence, not a computed truth value for a query or proof that a particular interaction satisfies it. The enum belongs to a reflected item-unlock condition structure; the probe has not established a complete grammar or a direct mapping for every progression-bundle query. The model chooses whether to interact with an observed station, research alternatives, or ask for help; code neither injects tool calls nor predicts completion. Empty, unreadable or unrecognized conditions remain unknown rather than false. No parser or semantic synthesis is necessary for this change.

Proposed files after review: `client_mod/scripts/crafting.lua`, `client_mod/tests/test_crafting.lua`, `brain/knowledge.py`, and focused knowledge tests. No change to the native reader, judge definitions, inventory, health, world state or recipe data is proposed. Changes to per-world persistent state require a separate backup and explicit design.

The existing Lua generator normalizes whitespace in bundle queries; 224 of 877 JSON queries differ byte-for-byte from the generated strings. The client can preserve the strings it receives exactly, but byte-identical JSON source text requires a separately reviewed generator change. The knowledge card format changes and therefore increments its existing index schema version so a normal initialization rebuilds the derived cached index; this does not clear world memory.

## Principles and acceptance

### Bounded card layout correction after full-gate failure

Gate62459 failed the existing real-data Bronze Bar regression: adding raw queries, readable duplicates and repeated generic context inside each recipe alternative made the900-character lookup clip retain only one alternative. Preserve the failing test. Keep compact recipe quantities/stations in `How to get`; put each recipe's exact queries and any useful readable rendering in separate atomic fields labelled with the recipe identity, with generic context once per item. Keep all query facts in the indexed full card. When a snippet cannot fit the detail fields, omit them as whole fields before discarding core recipe alternatives and explicitly say that full catalog conditions remain available through craft_plan/recipes. Never cut a query mid-expression, synthesize relations, increase the global context budget, or choose a recipe for the model. Small cards must still expose all queries; long cards must preserve complete core alternatives and an honest omission notice.

Additional actual queries: `site:sqlite.org fts5 snippet maximum tokens`; `site:docs.langchain.com context engineering summarization truncation context`. Opened [SQLite FTS5 snippets](https://www.sqlite.org/fts5.html#the_snippet_function) and [LangChain context engineering](https://docs.langchain.com/oss/python/langchain/context-engineering). SQLite documents bounded fragments selected for query terms, which do not guarantee complete recipe facts; LangChain distinguishes persistent tool state from transient model context. **Adapt** the existing structured-field clipper and card renderer; no new dependency or retrieval framework. Fresh independent review precedes the layout correction. Regression acceptance: existing real-data recipe-quantity test unchanged, synthetic long multi-recipe cards retain complete core facts with explicit omitted detail, full source cards preserve every raw query, and small lookup cards retain multiple queries. Then one integrated gate with the independently developed UI/rest fixes.

Implementation scope: retain the existing four-recipe card selection; the indexed card keeps every raw query for those represented recipes, each labelled by its recipe id. It is not a claim to include conditions for recipes outside that selection. Readable variants appear only when a class name changes, and shared progression context appears once. A clipped card drops condition fields atomically and protects an omission notice before trimming whole core alternatives; when even one alternative cannot fit it reports the count instead of cutting it. The unchanged craft/recipe tools remain the route to the complete catalog. Card schema 11 invalidates the prior cached format.
