## Decision

**Retain the existing two-speed native architecture and improve the information/action contract across it.** Reuse the game's native interaction detector, open-menu owner APIs, UI handlers, inventory evidence and current task board. Adapt modern semantic computer-use patterns into a compact, source-labelled entity/menu observation that preserves independent identities, freshness, unknowns, actions and verification. Build only missing generic readers/adapters demonstrated by a discriminating trace. No framework researched here supplies turnkey headless Dragonwilds perception or reliable interaction with overlapping chests.

The strongest immediate opportunity is **truthfulness and continuity of evidence**, not a new visual model. The code already detects nearby chest/station instances and prevents ordinary chest/station interaction presses on a different detector actor. Several failures can still arise before/after that protected press: same-name summarization, spatial-memory identity collisions, capped observations presented without coverage, failed external-inventory reads represented as empty, menu families whose owner is unknown, a separate crafting approach controller, and unverified cleanup. These are concrete static gaps; their frequency/impact requires measurement.

## Detailed code findings

### 1. Nearby enumeration has useful identities, but overstates perceptual coverage

`sense.lua:646-648` tests actor-origin Euclidean distance. The native enumerators describe currently loaded instances; they do not test the camera frustum or occlusion. Category caps occur at `739-742`; `totals` exist for ordinary actor categories, while foliage enumeration itself is already pre-capped (`683-690`), so even these totals are not a global foliage count. Do not label a radius census as visible, in sight or fully searched.

The state bridge passes category rows but loses census totals/radius/timing/completeness (`client_bridge.lua:400-404`). `look` returns `total=#things` **after** per-category capping, then a second final cap, with no count of entities omitted before matching. In a dense area a relevant farther object of the same category can disappear before its name is scored. A filtered look about a chest improves ranking inside that bounded set; it does not prove no other chest exists.

There is a loaded-actor id fallback (`852-875`), useful when a known id has fallen out of the census. It returns only a generic actor/go_to row; it does not reconstruct all interaction capability metadata. This is a distinction between identity resolution and affordance discovery.

Recommendation: carry observation time/source, radius, category counts/omissions and read status end to end; use detected rather than visible unless an actual tested visibility measurement exists. Preserve valid positive rows on partial reads. Return bounded-negative evidence explicitly. Query narrowing/pagination must happen before irreversible omission, or state the limitation. Do not scan every UObject at model cadence or add LOS traces to every row; first measure candidate-focused reads.

### 2. Same-name and same-cell reductions can erase the selected chest

`brain/situation.py:317-326` groups by display name, retains the nearest id/distance/note and adds counts. Consequently two identically named chests become one summarized group with one id. This is acceptable as a broad summary only if the model is told another id requires a focused look. It is inadequate as a unique container choice for a persistent task. `_line` clips to six groups / 240 characters, and `Usable`/`Stations` are optional under the 18-line limit (`789-802`). Important rows can exist in state but be absent from the guaranteed digest.

More serious: `MapMemory._key` (`brain/map_memory.py:82-85`) keys **kind + class-or-name + rounded 2 m XY cell**, ignoring both id and Z. Same-class close chests or objects on stacked floors can overwrite one memory record. The module docstring says “or by its stable id”, but the implementation does not. Because observe refreshes last_seen on the surviving merged record, its apparently fresh timestamp cannot distinguish which physical chest survived. This is a static collision mechanism, not a measured live incident.

`places.where` preserves source/seen_at and marks broad region estimates honestly, which should be retained, but remembered results are deduplicated by kind/name (`brain/places.py:357-366,390-393`). That is suitable for coarse place search, not selecting one of several same-name objects. Director `map_memory` (`director.py:459-462,507-514`) returns raw `last_seen` but exposes no age filter despite the underlying query supporting one. It should describe memory as remembered evidence and offer freshness/identity information without discarding historical knowledge.

Recommendation: independent persistent object records plus explicit spatial association/aliases; separate coarse area aggregation from actionable object identity. Validate session/native id again after streaming/restart, with world identity and position/elevation evidence; never assume UE short names are durable. Preserve memory with a backed-up migration if its schema changes. Do not “solve” this with a chest-name table or one workflow per container.

### 3. Actor origin, interaction location, bounds and feasible standing pose are different

Generic interaction already learned the important distinction. `sense.describe_interactable` may replace actor position with an interaction component location, retaining `actor_position` (`430-443`). `skills.W.interaction_point` prefers conventional collider properties then the interaction component (`297-318`), and generates standing offsets (`321-335`). `new_episode` binds this geometry once at action start. `episode_poll:548` retains the captured row; it is not a generic moving-target refresh service.

The current guards differ: sense checks a 3D component offset within 10 m; skills checks only XY within 10 m. A point passing that guard is still not necessarily the useful front surface, a walkable standing location, correct elevation or visible part of a large object. Capsule feet are now consulted by generic interaction's “on top” guard (`275-294,567-575`), a useful correction already present; do not re-propose it as wholly missing.

Crafting has a separate open/approach state machine (`crafting.lua:1104-1205`) using station row position and independent stand points. It checks 2D reach and exact detector identity but does not initially share `W.interaction_point`/collider candidate generation. This duplication can make generic interact and craft behave differently around the same station. Consolidating only the shared **approach + native focus** substrate is a plausible later repair; preserve specialized craft/processing verification and do not broaden this into a framework rewrite.

The game's own retained dump offers more promising diagnostics than guessing: `UInteractableDetectorComponent` declares `DetectionRange`, `InteractionRanges`, `CameraRayLength`, `CharacterTraceDistance`, `CharacterTraceCapsuleSizeMultiplier`, `CharacterTraceDownwardsAdjustment`, `CurrentInteractableCollider` and `CurrentWorldActor` (`Dominion.hpp:24476-24495`). The current observation returns actor/prompt but not collider identity/geometry. These declarations justify a narrow read-only experiment; they do not prove values or API safety in the installed runtime.

Epic documents `GetActorBounds` as whole-actor bounds and `GetClosestPointOnCollision` as a simple-collision query with distinct positive/zero/negative outcomes. Neither alone is the game's interaction eligibility test. Both have out-parameters; use the repository's native-marshalling lessons and game-thread validity fences before any live call. A component's generic bounds may be reusable diagnostic geometry; the actual detector remains the final press authority. [Actor bounds](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/GameFramework/AActor/GetActorBounds?application_version=5.5), [closest collision point](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UPrimitiveComponent/GetClosestPointOnCollision?lang=en-US).

### 4. Close-target protection exists; preserve it and extend attribution

For ordinary chests/stations, `same_target` requires the detector owner id to equal the chosen actor id (`skills.lua:245-251`). The face phase re-reads it before injecting real Enhanced Input (`inventory.lua:570-587`). When it cannot obtain focus after alternate spots it reports the competing target and approach evidence (`skills.lua:733-738`). This should not be replaced by “nearest chest wins” or silent retargeting. The prompt's id is necessary but not sufficient: it cannot repair an earlier summary/memory that presented the wrong object's id.

Exceptions deserve explicit semantics: foliage identity may match detector name/item until conversion; generic world-item interact accepts the same item id (`1390`); water may accept the same prompt (`400`). These are not evidence of exact physical-instance targeting. When an equivalent target is accepted, return requested and actual target identities distinctly. For chests no such fallback is justified merely because names match.

Recommended trace record: requested id and observation token; current resolved id/world; actor/interaction/collider positions; approach pose and tested route result; native detector actor/collider/prompt immediately before press; press/action id; active UI owner; selected slot/recipe; evidence delta; final modal/input state. This is causal observability for diagnosis, not internal-stat narration to the player.

### 5. Menu unknowns must survive the whole read/action loop

`input.observe_screens` (`147-157`) distinguishes unavailable/non-boolean native reads from no open screen. This is already the correct pattern. `open_screens` is a cleanup census that maps failed IsOpen reads to false; do not reuse it as proof a screen is closed. `M.SCREENS` enumerates specific menu families, while `modal` also tracks container, build, conversation and other input modes. This is not a universal UMG tree.

`skills.W.screen_target` recognizes only Crafting and Processing (`480-490`); Runecrafting, Enchanting, Composter and other screen types can be known-open but unknown-owner. Correct failure behavior is to retain “open screen; owner unverified/adapter unsupported”, not closed, empty or selected-target success. `W.open_station` and container `WorldInventoryAPI.InventoryComponent:GetOwner` already provide strong family-specific owner readers and can be adapted behind a generic owner observation shape.

Static useful declarations exist: `CraftingUIAPI.CurrentCraftRecipe` (`Dominion.hpp:18174`), recipe row `CraftingUISlotBase.ContainedRecipe` (`18201`), `ProcessingStationUIAPI.CurrentlySelectedSlot`, ingredients/fuel inventories and cached widget (`31165-31177`), and `ComposterUIAPI.ComposterComponent`/selected slot (`17524-17530`). These are read candidates, not permission to call setter/server functions or proof a menu exposes all recipe state while closed.

There is no need to force semantic handlers to click every tab when the game itself provides a legitimate menu handler for recipe selection. For unsupported mechanics, a reusable adapter should expose open family + owner + displayed options + enabled/selected state + real handlers. Avoid model tools containing guessed menu coordinates or a universal arbitrary UFunction-call capability.

### 6. External inventory readers still conflate unknown and empty

`inventory.external_rows` (`841-860`), `crafting.W.contents` (`768-788`) and bridge `contents_of` (`929-947`) initialize empty output, catch/ignore native read errors and return no read status. Positive partial rows can survive, but omitted rows and quantity defaults become indistinguishable from complete state. `take` then says “it's empty” when no matching rows were read (`skills.lua:1969-1975`). This is specifically contradicted by the accepted requirement unknown is not empty.

Personal inventory now has per-scope `read_status`, lower-bound quantities and unmapped-slot handling; reuse that established contract. Container/processing evidence needs status, world/controller/owner/component identity, observation time, complete slot cardinality and positive rows. A failed count/read cannot prove a zero, free slot or full container. “Observed item; quantity/slot unknown” can inform the model but is not actionable transfer authority.

Store/take already validates exact container owner after opening (`2002-2005`) and both inventories after a transfer, which is strong. However the transfer step's `press()` does not visibly re-read active menu owner before every subsequent UI handler, nor does `job.step` re-check it during the transfer phase. It retains the component acquired before approach. An interruption/owner switch or recreated inventory should invalidate/rebind the action explicitly. This is a static robustness concern; no live race was induced here.

### 7. Success and cleanup need separate observed evidence

Bench crafting has improved verification: a matching recipe path/count success event and output gain are required together, with native-count bindings checked across world/controller/pawn/component/asset (`crafting.lua:1318-1329,1353-1381`). This is stronger than “inventory grew” alone and should be the precedent for causal interaction outcomes.

Generic interact can accept an arbitrary inventory gain or disappearance as an effect (`skills.lua:752-789`), even for a menu-opening interaction. An unrelated magnet pickup could therefore be a confusing signal. Store/take has a later exact owner check, so it does not automatically transfer after an unrelated generic success. The model-facing generic result should still distinguish incidental inventory gain from “the requested menu opened”. Disappearance also needs a loaded/unloaded distinction before claiming the object was consumed/destroyed.

Container cleanup issues a close and releases immediately (`1923-1930`); crafting finish calls `W.close` in pcall, then clears `ui_open` and releases regardless of its boolean (`1694-1702`). Input orphan/after-action guards improve recovery, but a successful item operation can be reported while final input state remains unresolved. Return separate operation outcome and cleanup status; bounded close/readback must not erase a real transfer/craft or invent clean gameplay readiness. Preserve exactly one owner through the cleanup transition.

### 8. Long tasks need current relevant evidence, not more scripted workflows

The Director/task board/research loop already exists. The right intervention is to feed it enough relevant current observations and explicit failures. `controller.next_turn` refreshes position/vitals/inventory plus up to six station identities (`375-418,843-865`), but no nearby independent container list, open-menu owner/state, collider focus or scene coverage. It also retains previous tool messages, so stale observations coexist with the new continuation. An id being present in history is not current visibility or reachability.

`crafting.state_extras` caches station state for five seconds, keeps at most four stations, and can reuse old distance/content values (`1823-1854`) without an observation-age marker in each row. The Director can retrieve remembered places but cannot ask map_memory for a max age via its exposed schema. Repeated gather/deposit/craft jobs need current operation-specific evidence and persistent remembered location/source, with both ages visible. A compact relevant-target section should be guaranteed within the observation budget; dumping all raw state is unnecessary.

Exploration (`skills.lua:1756-1847`) is eight compass headings, 30 m default legs, least-visited 10 m cells and census matching. It does not represent visibility coverage, navigable frontiers, unexplored versus occluded areas, object-search completeness or task utility. It reports “in sight/saw nothing” despite no LOS. Preserve it as a bounded search heuristic/diagnostic. Build a richer exploration service only after terrain/navigation observations expose the real unknown/frontier structure; the Director chooses task-relevant regions from knowledge/needs, rather than code assigning resource-specific tours.

## Proposed generic observation/action contract

This is an architectural recommendation for review, not implemented behavior. Extend existing observation/result structures rather than expose one tool per menu/chest or dump the entire UObject graph.

1. **Observation envelope:** world/session identity, observed_at or monotonic tick, source, status complete/partial/unknown, query scope/radius, returned/omitted counts and bounded reasons. A stale value keeps its historical timestamp; reading it again does not make it current.
2. **Entity:** distinct observed/native id plus persistent association, display name/class/kind, actor origin, interaction part/collider when observed, position/elevation, detection source, visibility unknown/occluded/visible only when actually checked, and supported actions with known conditions. Bounds, reachability and focus are separate facts.
3. **Menu:** family/type, open/closed/unknown, owner identity or owner-unknown, input mode, current page/tab, selected item/recipe, displayed options/slots, enabled/disabled/unknown and read coverage. Family adapters preserve raw native provenance without inventing missing semantics.
4. **Action request/result:** requested id/observation; actual focused id immediately before input; owned UI target; selected slot/recipe; exact native action path; pre/post observed evidence; operation outcome; cleanup outcome. Invalidate/rebind after world/pawn/owner/component changes.
5. **Model view:** a guaranteed compact section for the active target/menu and the task-relevant alternatives, plus explicit omissions and read tools. Keep broad summary grouping for orientation; never let it erase the unique object on the task board.

The model still selects intent, destination, alternatives and sequence. Native code may validate that its actuator is about to operate on the model's chosen object and report failure truthfully; it must not silently choose a different chest, remap the player's wording, insert benchmark hints or complete state by writing inventory/damage. A new crop/recipe using the same menu should require game data/research and a model plan only. A new screen family can justify one reusable adapter.

### Resources and compatibility

Repository operating documents describe an 8 GB VM with one client/server and memory/commit pressure; current hardware/GPU capacity was not independently measured in this worker. Native reflected reads reuse an already working process/runtime and avoid rendering/model weight costs. Bounded source/identity/coverage fields should be cheaper than a screenshot+OCR+VLM loop, but payload/latency must still be measured. Do not claim a specific token or speed improvement without an A/B trace.

Local OmniParser/other visual models, a rendered client and RTX-oriented inference add dependencies and memory/GPU demands. Remote inference moves weight memory off-host but does not produce missing pixels and still spends budget/latency. CPU/software rendering may exist at engine level but has no proven usable performance here. Headless native observations should therefore remain the default; render only as a carefully admitted fallback for information demonstrably unavailable through native sensors.

No large scene-graph package, database, multi-agent orchestrator, new model family, raw memory patch or framework migration is justified by this audit. A small temporal entity/menu/effect representation can use the current bridge/state/task memory. Adopt an external library only if a held-out fixture shows a measurable benefit over that incremental path.

## Review against PRINCIPLES and handoff

- Real player paths: preserve input injection and native client UI handlers; no direct server RPC, item/health writes or emulated effects.
- Model infers: native code reports state/availability/target mismatches; the Director/Controller own plans and alternative choices.
- Genericity: entity identity, geometry, menu ownership/read completeness and operation evidence apply to all chests/stations; data and model plans cover new items/recipes.
- Two speeds: native bounded observation/actuation and per-frame checks; model decisions at events/task boundaries.
- Verified state: distinguish detected/visible, remembered/current, partial/complete, empty/unknown, requested/actual, operation/cleanup. Keep frozen judges intact.
- Persistent knowledge: preserve per-world data and back up any memory-schema migration; no blank replacement to hide failure.
- Verification: report-only work; no tests run and no new live/autonomous pass claimed.
