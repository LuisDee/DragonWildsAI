# Long-job gaps as negative tests (2026-11-17)

The survey in `docs/GOAL-2026-11-17-long-jobs.md` ("Where it stands") found ten gaps by reading the code. Each one is now a unit test in `tests/test_long_job_gaps.py` that fails on today's code. Every gap test is marked `xfail(strict=True)`, so the suite stays green today. When a fix lands, the test XPASSes and the strict mark fails the run: the fixer removes the mark and the test then guards the fix. Nothing in `brain/`, `client_mod/`, `tools/` or the existing tests was changed. The tests make no model calls. They use `tests/conftest.py` `Rig` (the mock game with scripted Controller and Planner) and the Director fakes from `tests/test_director.py` (`make`, `ManualExecutor`, `ticks`).

I checked each xfail with `pytest --runxfail` to see the real failure. Each one fails on the gap's own assertion, not on a setup error. Today the file gives 2 passed and 13 xfailed in about 5 s.

## What the survey got wrong or narrower than stated

- **9, the roof:** wrong as written. The plan names the roof rule and sorts by it. The only part missing is the live state of his own wheel's roof, and the model already reads that elsewhere. The xfail for it is optional work. If the decision is that the plan should not duplicate `bases_line`, delete that test.
- **6:** right, with one detail. `needs.py:399` is the "Need load" (over weight) line only. No pressing need is raised for a bag full by slots (`pressing()` has no slot check), so `inventory_full` has no options line at all, remembered chests or not. Gap 4's test covers how the job ends, not that line.
- **5:** right, and the boundary is exact: 5 attacks give "done" and 6 give "stuck".
- **2:** right, and slightly worse than stated. `StateStore` does read `task_tree.json` back (`store.tree` is set on the new brain), but nothing uses it, and the new brain makes no model call at all.

## Where `containers_remembered` is set, and its type

Exactly one writer: `brain/stash.py:62`, `Stash.observe_state`, which sets `data["containers_remembered"] = self.labels()`. That is a `dict[str, list[str]]`, `{"your Crate at (104,1858)": [item ids]}`. Three readers: `brain/situation.py:1100` and `brain/director.py:470` pass it to `gear_plan.plan(stash=...)`, which wants this dict and works. `brain/needs.py:399` wants a list, so it never matches.

## Tests tied to the default path

If the board becomes the one holder of a job (the research note's direction), these tests are **deleted, not turned green**: 1 (`_open_request` and `request_closed`), 3, 4 and 5 (`Agent.run_goal` outcomes). The board equivalents are new tests on `Director` with the `test_director.py` fakes: a step preempted on death, the job not parked after three deaths, the job survives six fights, and a step run with no call that leaves the task open. Test 2 is partly tied: it builds an `Agent` but accepts any sign that the ask survived. Tests 6, 7, 9 and 10 are board-neutral or board-side, and stay.

## Could not be written

None. Every gap was reached through public functions or through the fakes the existing tests use. Two notes on fidelity:

- Test 2 swaps the mock game's class to make `go_to` raise a `BaseException`. `GameInterface.call` looks tools up on the class, so an instance attribute does not work. This stands in for the process dying. It does not model a real kill: there is no partial write and no lost log tail.
- Tests 3 to 5 use `MockGame.script_failure`. The mock has no respawn or grave, so a fixed death path is judged only on the job's outcome, not on the grave or the "what killed you" message. Those need a live trial (I3 in the goal).
