## Strongest case for the existing design

The division of responsibility is appropriate: models choose destinations and work; native character inputs perform locomotion; the DEV native planner supplies broad routes; client collision handles local replicated geometry; per-world routes and directed traversal links should preserve experience. A headless client without its own NavigationSystem reasonably reuses the server's navigation instead of constructing a new world mesh.

There are substantial safeguards worth retaining. The oracle uses one epoch/nonce offer and serial ownership (`tools/nav_oracle.py:287–365`); the mover binds actions to owner, generation, pawn and world (`move.lua:796–843`). Long movement no longer silently degrades into raw straight-line input after losing its route. Arrival rereads the real pawn and destination and requires life/ground evidence (`move.lua:1297–1326`, `1803–1816`; `client_bridge.lua:562–584`). A partial endpoint is reported as failure rather than arrival. Local planning already has two floor samples, slope/step discrimination, typed jump edges, finite sampling and lazy edge checks (`localplan.lua:89–106`, `173–190`, `311–392`). Jump and Windstep execution include ownership and landing checks; measured envelopes and actual unlocks are preferable to guessed movement powers.

Those features are a sound base. Their problem is inconsistent evidence contracts between layers, not absence of every required subsystem.

## Severity-ranked findings

### 1. P1 — native route availability is confused with movement authority

**Confirmed source conflict:** `move.lua:1527–1539` permanently requires native authority for a normal trip beyond 10 m or above the single-jump threshold, clearing other route state. At `1747–1769`, a missing/ended native route returns before ordinary memory, trail or recovery selection. The independent local-observation alternative is limited by **original** goal distance to the 9 m local window (`1676–1679`).

Memory's advertised first-choice long-trip branch is guarded by `not st.nav_required` (`2011`), yet only considers general routes beyond 30 m (`2031`). With normal native routing enabled, these conditions cannot both hold. Leader trail entry is also guarded by `not st.nav_required` (`2053`). A late memory retry at `2750–2766` can occur while a native route still exists; it cannot rescue a required route already exhausted above. This is more precise than saying memory is never used: short/direct movement and some earlier/still-valid-route states can use it.

**Strongest defense:** these gates stopped unverified straight-line fallback and stale-route input. Removing them globally would regress a real safety property.

**Minimum repair:** retain ownership admission, but make admitted evidence describe a particular executable segment rather than equating all valid authority with one planner. Native, genuinely traversed memory and a freshly verified local segment can propose candidates under the same pawn/world/life/goal contract. Preserve the original goal and report partial progress separately. Admission must validate the current-to-segment connection and floor; memory cannot become authoritative merely because it exists. This is a narrow route-contract repair, not permission for unrestricted wandering or overriding model intent.

**Falsifiable test:** with a long goal, an exhausted native partial path and a valid remembered alternative, the current source terminates before selecting it. A repaired system must select and validate that alternative, or report the concrete missing connection. Negative controls: stale memory, a wall in its connector, wrong floor, changed life/world and no candidate all produce no unverified input. See findings 3 and 4 before enabling memory as an independent source.

### 2. P1 — waypoint advancement can erase the essential detour

`move.lua:709–723` advances when the pawn is within radius **or** is closer to the next point than the current point is to that next point. That second condition is not proof of passing the current waypoint, being inside the path corridor, or having a walkable shortcut. It applies to native (`1647`), local (`2202`), trail and memory (`2372`) routes.

Counterexample in metres, same floor: pawn A `(0,0)`, required corner B `(10,0)`, next corner C `(0,10)`. The current predicate skips B immediately because `|A−C|=10 < |B−C|≈14.14`, even if the diagonal A→C is blocked. Enlarging permitted vertical error by `0.9 * distance_to_point` (`715–719`) also allows distant points on other levels to be skipped under this condition. A path made of correct points is not preserved by this executor.

**Minimum repair:** removing the unproven next-nearer branch while retaining reached-radius, floor and traversal-endpoint requirements is a defensible first patch. It must be tested for overshoot/oscillation at real speed. Any future pass-through shortcut needs bounded lateral/vertical error and validated corridor/segment continuity, not another distance-to-goal heuristic. Do not “fix” an unreachable floor point by skipping it.

**Discriminator:** pure actual-module tests with the triangle above, a U-shaped detour, a switchback ramp, same XY on separate floors, and a fast overshoot. First prove the correct path index stays at B and that input direction uses it. Then developer-drive a held-out corner/slope. The newly reproduced native partial endpoint proves this defect is not the sole root cause of the ramp episode.

### 3. P1 — stored routes are proposals, not certificates of connected traversability

**Now directly implicated by a live control:** trap t7 has centre `[83.37,1873.78,-32.15]`, radius 8 m, vertical band `[-35.151,-30.651]`, status `verified`, `n_ok=58`, and first exit floor point `[80.79,1873.5,-35.68]`. `navmem.lua:202–208` tests a broad cylinder/band; `214–218` copies its exit without a current-entry connection check. `move.lua:2029` immediately selects it. At `2379`, adding the follower half-height converts that floor point to the observed centre aim Z −34.80: the conversion is internally consistent, but the chosen entry is 3.27 m below the current centre. Thus merely adjusting centre/feet units cannot repair this particular choice.

The subsequent “perched” detector (`move.lua:2640–2657`) treats three of four nearby low/missing floor rays as reason to issue a jump and step off. It does not establish that stepping off follows an admitted, supported route toward the requested floor. A sparse-support pattern is not a sufficient rescue plan. This is the strongest current end-to-end causal evidence: broad trap membership → unverified lower-floor exit entry → stuck → step-off input → lower level. Retain the underlying trace and mark the trap's applicability/entry evidence; do not erase t7 or hard-code its coordinates. A generic entry/segment validator must precede reuse, and recovery must preserve the same floor/route evidence requirements rather than escape them.

`navmem.lua:315–316` joins nearby points from different routes within 4 m/1.2 m height without collision validation. `327–329` attaches start and goal to any remembered point within 15 m, again geometrically; `353` appends the raw goal. A route can therefore be “found” through a wall or across floors. `162–170` simplifies by spacing, not corner visibility; sampled endpoints do not prove the resulting chord. Reverse edges at `291` exclude jump/djump but not recorded drop edges, so a descent may become an impossible ascent.

The capture side can destroy discontinuity evidence: `move.lua:885–892` removes airborne/gap samples and puts the remaining samples into one route, creating a chord over the omitted crossing. It also subtracts **the follower's** half-height from leader centres. Ground-read errors are accepted as grounded in own-trip sampling (`1877–1891`). These do not prove the saved ramp demonstration was bad, but they disprove the general assumption that every saved edge is a known walk.

**Minimum repair:** preserve observed segment boundaries and direction, provenance, coordinate frame and uncertainty; validate unknown connectors and simplified chords lazily through the existing client planner/geometry adapter. Failed edges need evidence-based invalidation. Keep the per-world store and graph search. Do not delete memories, blanket-ban learned routes, or treat `n_used=0` as selection evidence: no demonstrated counter increment currently supports that inference.

**Negative controls:** two routes separated by a thin wall; a demonstrator jumping a gap; down-only ledge reversal; different capsule heights; dynamic construction blocking a previous route; interrupted/unknown ground reads; and wrong-world memory. Distance-based graph connectivity must not pass any of these by itself. OMPL's separation of state and motion validation is useful precedent, not a proposed new runtime dependency.

### 4. P1 — local “verified” paths still do not establish capsule clearance

The local planner is better than a single floor layer, but its evidence is sparse point geometry. `localplan.lua:92–106` takes two downward line hits and assumes the lower floor lacks headroom if they are closer than `head`. `311–392` checks essentially knee/high horizontal lines and one midpoint for a slope. It does not sweep the character footprint or check shoulder/head clearance for a doorway. `move.lua:395–443` strengthens result shape/ownership for observation but still supplies line traces. `envelope()` reads step and jump, not a live walkable slope or capsule-radius clearance policy; `localplan.lua:58,179` falls back to 190 cm headroom and slope coefficient 0.9.

More directly, `move.lua:389,442` labels `Distance < 0.5` as initial penetration and `cell_floors` discards that hit. Existing [typed floor controls](r26-floor-observations-20261028.md) demonstrate that zero distance can occur both with no hit and penetration, and negative floor distance can coexist with walkable/nonpenetrating evidence. The old shortcut is not a general penetration truth source. The exact floor-query result is not identical to every line-trace result, so this is a reason to validate that assumption, not proof it caused this particular ramp failure.

**Minimum repair:** reuse the existing typed `floor_read.lua`/native floor evidence and collision profiles after their lifecycle contract is satisfied. Add only the capsule-aware support/clearance observation required by a demonstrated local rejection or false acceptance. Keep unknown distinct from clear. Read actual dimensions and movement constraints; do not globally turn on complex traces or alter character physics. Native floor support is also not full path/overhead-clearance proof.

**Discriminator:** compare the proven manual-climb line and doorway against selected floor layers, native current-floor normals/flags, capsule dimensions, edge rejection and the actual input path. Include a narrow doorway where centre rays clear but capsule cannot fit, overhead lintel, thin obstacle, stacked floors and steep nonwalkable surface. Do not claim the doorway and ramp share one cause just because they are nearby.

### 5. P1 — a short upward nav segment is fabricated into a jump link

`move.lua:1620–1622` sets `link=true` for any adjacent points rising over 60 cm with a horizontal run under 3 m. `2398–2406` then issues `Jump`. A 1 m rise over 2 m of continuous ramp meets this rule despite requiring no jump. Conversely, the actual directed/typed nav-link identity is absent from the wire payload; a drop/gap's requirements cannot be reliably reconstructed from these coordinates alone.

This is a concrete alternate explanation for apparent jumping. It is not proof it triggered on the recorded problematic point. There are other explicit jump sources: forward low-obstacle reflex (`2519–2528`), stuck recovery, local typed jumps and airborne leader crumbs (`2357–2365`). `traverse_learn.lua:413–426` estimates other players' actions from jump-count/velocity/rise and `440–445` emits inferred input records. Its improved stale-count baseline handling (`716–745`) is valuable; inferred input remains different from observed self input.

**Minimum repair:** preserve real nav-link metadata if an available reflected API can expose it; otherwise classify the segment through verified local traversal geometry and current capabilities, labelling uncertainty. Reuse typed traversal execution and landing proof. Do not add more jump retries or infer a jump merely from rising Z. Keep `traversal_moves.lua` as a capability/data profile; no ramp-specific spell routine is needed.

**Controls:** continuous ramp with those point dimensions must walk; real step above MaxStepHeight must require the supported traversal; forbidden/unmeasured double jump must not be inferred from a nav edge; fall without submitted jump must be recorded as fall/unknown rather than issued jump. Correlate monotonic input submission, ground/movement mode, vertical velocity, apex and landing by action generation.

### 6. P2 — correct detour progress is misclassified; replan requests can be inert

Native advancement occurs at `move.lua:1647–1648`, but the later native branch sets `local i0 = st.wp` then tests `st.wp > i0` without modifying it (`2394–2395`). That condition cannot credit a crossed native waypoint. The five-second watchdog (`2696–2704`) otherwise measures projection toward the **final** goal. A legitimate detour away from that goal can reach native waypoints yet enter recovery. A long native segment can also progress correctly away from the final goal for over five seconds without crossing a waypoint.

Separately, every `nav_force` occurrence is an assignment (`1112`, `1128`, `1491`, `1800`, `2000`, `2120`, `2172`, `2376`); no code reads it. Thus comments promising a forced oracle requery after local failure are not an implemented invalidation path. Existing binding guards prevent stale owners; they do not prove route geometry is still current.

**Minimum repair:** credit advancement where it occurs and track bounded monotonic progress along the currently admitted segment/path, retaining separate physical-stuck and overall-time limits. Replace the inert flag with explicit bounded route invalidation/requery on an observed changed/failed route. Requery is not progress, and repeated identical evidence should retain failure history instead of resetting the budget. Do not simply increase timeout.

**Tests:** a necessary retreat around a U-shaped obstacle; a long segment pointing away from final goal; oscillation at one waypoint; an unchanged failing query; local failure while original native route is still present. The first two must progress; the latter three must terminate or surface a concrete blocked state.

### 7. P2 — named-target failures lose the route evidence the model needs

`move.lua:1195–1198` attaches terminal route feedback only when `st.goal` exists; named goals use `st.target_name`. `status()` repeats the `st.goal` requirement (`3263`). Meanwhile metadata collection requires exact equality with the requested target coordinates (`1605–1607`), although moving-goal route refresh uses a 3 m threshold (`1552–1555`). The repeated named-target failures therefore return a generic route-ended detail without the endpoint/error facts seen on the nearby explicit-coordinate attempt. Brain trace line 1224 contains partial, endpoint, projected-goal and vertical error for the coordinate action; lines 1363/1399/1422 do not for the named action.

`brain/controller.py:1119–1124` deliberately suppresses the specific verification failure in immediate fallback speech, producing “Sorry, I couldn't walk somewhere.” That is a truthful failure but does not meet the specific-reason communication contract. The newer `next_turn` **does** append current observations (`843–864`); the old Sol audit's absence-of-continuation-state defect should not be repeated as a current finding.

**Minimum repair:** retain distinct requested target identity, route-query snapshot/time, current target observation and measured final position. Report their differences without representing stale snapshots as current. Give the model the specific planner outcome and bounded failure history; preserve a single specific plain-language failure. Do not add phrase rules that force `follow` or replace the destination. A follow request and a one-shot go-to remain different model-visible intents.

### 8. P2 — source identity checks do not define a usable moving-goal/arrival contract

`local_route_owned` requires exact current target XYZ equality repeatedly (`811–842`). Even small movement can invalidate an observation while a short local route is being sampled. The native route uses a looser replanning threshold and does not retain/revalidate the actual request start in `nav_pending` (`561–562`) against later displacement. Holding inputs prevents most self movement while waiting, but inertia, knockback and server correction are competing causes worth testing. These are potential starvation/stale-start failures, not established causes of the stationary repeated endpoint.

Coordinate goals, actor origins and floor waypoints have different frames. `reached()` permits vertical error up to twice half-height (`1300`, about 1.76 m), while native waypoint advancement compares nominal feet (`1647–1648`). That tolerance catches the observed 3.28 m error but does not by itself prove the same floor or a usable lodestone interaction point. A character's actual contact plane can differ from centre minus half-height by floor distance and slope geometry. Fixed Z alone is not a complete floor identity.

**Minimum repair:** name the frames in the route/goal contract; keep actor identity separate from mutable pose. Bind a finite local segment to its observation version and invalidate/replan when target drift changes its intended endpoint materially, while retaining strict pawn/life/world/owner checks. Verify terminal actor proximity or requested point under that contract and, for a lodestone job, actual same-floor interaction reachability. Do not solve ambiguity with an XY-only interface, a widened Z tolerance, or hidden replacement by the projected floor.
